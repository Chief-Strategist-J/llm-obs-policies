# Part 2: Querying, graph algorithms and reasoning (#51–100)

Same format and the same contract (roles; rules K1–K8; guardrails KG1–KG6).

## B1. Query languages and execution

### 51. SPARQL 1.1 (W3C)

**Definition:** The W3C standard query and update language for RDF graphs.

**How it works:**
1. A query states triple patterns with variables, the basic graph pattern: `?p :worksFor ?org . ?org :locatedIn :Paris`.
2. The engine finds every variable binding that makes all the patterns match the data, effectively a join of the patterns.
3. Extra clauses: `OPTIONAL` (left join), `FILTER`, `UNION`, `MINUS`, aggregates with `GROUP BY`, subqueries, property paths (#58) and `SERVICE` for federation (#59).
4. Query forms: `SELECT` (a table), `CONSTRUCT` (a new graph), `ASK` (yes or no), `DESCRIBE`.
5. SPARQL Update adds `INSERT`, `DELETE` and graph management operations.

**Agent use:**
- **Role:** Retriever (queries) and Curator (updates).
- **How:** The agent generates SPARQL from questions (#151), validates it against the schema, and runs it with limits.
- **Rules:** Every query has a `LIMIT` and a timeout (K6). Updates run only through the Curator's validated write path.
- **Guardrails:** Agents never run `DELETE`/`DROP` generated by a model without review (KG3). Use separate read-only and write credentials.

### 52. Cypher / openCypher

**Definition:** A declarative property-graph query language built around ASCII-art patterns, with an open specification (openCypher).

**How it works:**
1. Patterns are drawn as `(a:Person)-[:WORKS_FOR]->(o:Org {name: "Acme"})`.
2. `MATCH` finds subgraphs matching the pattern. `WHERE` filters, and `RETURN` projects results.
3. `OPTIONAL MATCH` works like a left join. Variable-length paths look like `-[:KNOWS*1..3]->`.
4. Writes: `CREATE`, `MERGE` (match or create, #172), `SET`, `DELETE`.
5. The planner chooses start nodes by index (#22), then expands and joins.

**Agent use:**
- **Role:** Retriever and Curator.
- **How:** The most common target language for text-to-query on property graphs (#151). Models are generally good at writing it.
- **Rules:** Variable-length patterns always get an upper bound (`*1..3`, never `*`). Pass values as parameters (#61).
- **Guardrails:** Unbounded `MATCH` patterns over supernodes can stall the database (KG4). Enforce query timeouts server-side.

### 53. GQL (ISO/IEC 39075:2024)

**Definition:** The ISO international standard query language for property graphs, published in 2024.

**How it works:**
1. Pattern syntax similar to Cypher, with standardized semantics.
2. Graph types (schemas), multiple graphs, and path modes that control repetition: `WALK`, `TRAIL` (no repeated edges), `ACYCLIC` and `SIMPLE` (no repeated nodes).
3. Path selectors such as `ANY SHORTEST` and `ALL SHORTEST`.
4. SQL/PGQ (part of ISO SQL:2023) brings similar graph pattern matching into SQL over relational tables.

**Agent use:**
- **Role:** Retriever.
- **How:** As vendors adopt it, the agent can target one standard language across graph databases, which reduces vendor-specific prompt and validation logic.
- **Rules:** Prefer explicit path modes (`TRAIL` or `ACYCLIC`) so traversals can't loop forever.
- **Guardrails:** Support for parts of the standard varies by product. Validate queries on the actual engine.

### 54. Gremlin (Apache TinkerPop)

**Definition:** A step-by-step traversal language for property graphs, from the Apache TinkerPop project.

**How it works:**
1. A traversal is a chain of steps: `g.V().has('name','Acme').in('worksFor').values('name')`.
2. Each step transforms a stream of "traversers" (objects moving through the graph).
3. Steps include filters (`has`, `where`), navigation (`out`, `in`, `both`), branching (`union`, `choose`), loops (`repeat` with `until` and `times`) and aggregation.
4. It runs on many TinkerPop-compatible databases, embedded or remote.

**Agent use:**
- **Role:** Retriever.
- **How:** Useful when the target database is TinkerPop-based, or when the agent builds traversals step by step as tool calls.
- **Rules:** Every `repeat` has a `times()` or depth-limited `until()`.
- **Guardrails:** Don't allow arbitrary lambda steps (custom code) from model-generated traversals. Treat them as code execution.

### 55. Subgraph pattern matching (VF2 / backtracking)

**Definition:** Finding every place in the data graph where a small query pattern graph appears.

**How it works:**
1. The query is a small graph: nodes with labels and constraints, edges with types.
2. Order the query's nodes by selectivity: start from the most restrictive (#57).
3. Backtracking: assign a data node to the first query node, then extend to the next query node using only neighbors consistent with the edges already matched.
4. Prune early. VF2 checks degree and neighborhood compatibility before going deeper.
5. On a complete assignment, output a match. On a dead end, backtrack.

**Agent use:**
- **Role:** Retriever.
- **How:** This is what every `MATCH` and basic graph pattern does underneath. Patterns with selective start points run fast; vague patterns explode.
- **Rules:** Anchor patterns at a specific entity or an indexed property whenever possible.
- **Guardrails:** Cyclic patterns (triangles, squares) over dense regions can produce huge result sets. Always limit them (K6).

### 56. Worst-case optimal joins (Leapfrog Triejoin)

**Definition:** A join algorithm that processes one variable at a time across all patterns, avoiding huge intermediate results on cyclic queries.

**How it works:**
1. Classic plans join two patterns at a time. For cyclic patterns like triangles, an intermediate result can be much larger than the final answer.
2. Worst-case optimal joins fix a variable order (a, then b, then c).
3. For the first variable, intersect the sorted values from every pattern containing it. Leapfrog search jumps between sorted iterators, like galloping intersection.
4. For each value, move on to the next variable, restricted by the bindings so far.
5. The runtime is bounded by the maximum possible output size (the AGM bound), not by intermediate blow-ups.

**Agent use:**
- **Role:** Retriever (engine selection).
- **How:** Engines with these joins handle cyclic and complex patterns (fraud rings, triangles) far better. The agent prefers them for analytics-style pattern queries.
- **Rules:** Mostly an engine property. Know whether your engine has it.
- **Guardrails:** None specific.

### 57. Join ordering and cardinality estimation (query plans)

**Definition:** Choosing the order in which a query's patterns are evaluated, based on estimates of how many results each produces.

**How it works:**
1. Statistics: counts per label, per predicate and per property value, plus degree distributions, and sometimes characteristic sets (which predicates tend to appear together on a subject).
2. Estimate each pattern's result size and the result size of joins.
3. Search for the cheapest plan with dynamic programming or greedy heuristics: start with the most selective patterns.
4. The engine shows the chosen plan through `EXPLAIN` or `PROFILE`.
5. Bad estimates (correlated properties, skewed degrees) cause bad plans.

**Agent use:**
- **Role:** Retriever and Observer.
- **How:** For slow queries, the agent reads the plan to see where the rows explode, then rewrites the query: add an anchor, reorder, add a label, or create an index.
- **Rules:** Profile new query templates before using them in production.
- **Guardrails:** Keep statistics up to date after bulk loads. Stale statistics cause sudden plan regressions (#188).

### 58. Regular path queries and property paths

**Definition:** Queries that match paths whose edge sequence follows a regular expression, such as "one or more `subClassOf` edges".

**How it works:**
1. SPARQL property paths: `:a :knows+ ?x` (one or more), `:a (:p/:q)* ?x` (repeated sequences), `^:p` (the inverse direction), `:p|:q` (alternatives).
2. The engine turns the expression into an automaton.
3. It explores the graph and automaton together (a product graph), using BFS (#63) with a visited set.
4. SPARQL's arbitrary-length paths return distinct endpoints, not every path, which keeps evaluation tractable.

**Agent use:**
- **Role:** Retriever.
- **How:** Powerful for hierarchies ("all subcategories"), org charts and part-of chains, without writing explicit loops.
- **Rules:** Constrain the start node and the edge types. Prefer bounded repetition where the language supports it.
- **Guardrails:** `*` over generic or dense predicates can visit the whole graph. Enforce a timeout and a result limit (K6, KG4).

### 59. Federated queries

**Definition:** One query that combines data from several graph endpoints or databases.

**How it works:**
1. SPARQL `SERVICE <endpoint> { … }` sends a subquery to a remote endpoint.
2. A federation engine decides which sources can answer which patterns (source selection), using metadata or test queries.
3. It ships bindings between sources (bound joins) to reduce transferred data.
4. It merges the results locally.
5. Performance depends heavily on network and source selectivity.

**Agent use:**
- **Role:** Retriever.
- **How:** Lets the agent combine internal facts with external reference graphs (a public knowledge base) without copying everything.
- **Rules:** Cache stable remote reference data. Record which source provided which facts (K1).
- **Guardrails:** Never send internal identifiers or sensitive values to external endpoints (KG2). Remote endpoints can be slow or unavailable, so set timeouts and fallbacks.

### 60. Ontology-based query rewriting (OBDA, OWL 2 QL)

**Definition:** Answering queries over an ontology by rewriting them into queries over the underlying databases, without copying data into a graph.

**How it works:**
1. An ontology (OWL 2 QL profile) describes the domain; mappings (R2RML, #42) link it to relational tables.
2. A user query over the ontology is expanded using the ontology. A query for `:Person` also covers `:Employee`, `:Customer` and other subclasses.
3. The expanded query is translated through the mappings into SQL.
4. The databases execute the SQL, and results are returned as graph answers.
5. The data stays fresh because it's never copied.

**Agent use:**
- **Role:** Retriever and Operator.
- **How:** Gives a graph view over live operational databases, which suits cases where copying the data is impractical or forbidden.
- **Rules:** Keep the ontology within OWL 2 QL so rewriting stays tractable.
- **Guardrails:** Large hierarchies make rewritten SQL big. Monitor database load (KG4).

### 61. Parameterized queries and query templates

**Definition:** Separating query structure from values, so values are passed as typed parameters instead of being pasted into the query text.

**How it works:**
1. The query text has placeholders (`$name`, `?name` with bindings).
2. The values are sent separately, with types.
3. The engine parses and plans the query once, and can reuse the plan.
4. Values can't change the query structure, which prevents injection.
5. Templates are pre-reviewed queries with parameters (for example "employees of org X").

**Agent use:**
- **Role:** Retriever.
- **How:** For frequent question types, the agent fills reviewed templates instead of writing free-form queries: safer, faster and more predictable. Free-form generation is the fallback (#151).
- **Rules:** Never concatenate user or model text into query strings; always use parameters.
- **Guardrails:** Template parameters are still validated (types, allowed values, length).

### 62. Pagination and result caching

**Definition:** Returning large results in pages, and reusing results for repeated queries.

**How it works:**
1. **Offset pagination** (`SKIP`/`OFFSET`) re-runs the query and discards rows, so it gets slower page by page.
2. **Keyset pagination:** order by a stable key and ask for "rows after the last key seen". It costs the same for every page.
3. **Result caches** are keyed on (normalized query, parameters, graph version, user's permissions).
4. A new graph version invalidates entries automatically through the key.

**Agent use:**
- **Role:** Retriever.
- **How:** The agent reads large results page by page within its context budget, and repeated lookups come from cache.
- **Rules:** Use keyset pagination for large scans. Include permissions in cache keys (KG1).
- **Guardrails:** Never share cached results across users with different access rights.

## B2. Traversal and path algorithms

### 63. Breadth-first search (BFS)

**Definition:** Exploring a graph level by level from a start node: all neighbors first, then their neighbors, and so on.

**How it works:**
1. Put the start node in a queue and mark it visited.
2. Take a node from the front of the queue.
3. For each unvisited neighbor (optionally filtered by edge type and direction), mark it visited, record its parent and distance, and add it to the back of the queue.
4. Repeat until the queue is empty, the target is found, or the depth limit is reached.
5. In unweighted graphs, it finds the shortest path (fewest hops) to every reached node.

**Agent use:**
- **Role:** Retriever.
- **How:** The basis of k-hop neighborhood retrieval (#157): "everything within 2 hops of this entity". Also finds the shortest connection between two entities.
- **Rules:** Always set a depth limit, an edge-type filter, and a cap on nodes visited.
- **Guardrails:** BFS through a supernode can visit millions of nodes in one step. Cap neighbors per node (KG4, #180).

### 64. Depth-first search (DFS)

**Definition:** Exploring a graph by going as deep as possible along each branch before backtracking.

**How it works:**
1. Start at a node and mark it visited.
2. Go to an unvisited neighbor and repeat from there, using recursion or a stack.
3. When a node has no unvisited neighbors, backtrack to the previous one.
4. Record discovery and finish times, which reveal cycles (an edge to a node still in progress), give topological order, and identify strongly connected components (#80).

**Agent use:**
- **Role:** Retriever and Reasoner.
- **How:** Used for cycle detection (circular dependencies, circular ownership), dependency ordering and exhaustive path enumeration in small subgraphs.
- **Rules:** Use an explicit stack in implementations, to avoid recursion limits on deep graphs.
- **Guardrails:** Path enumeration grows exponentially. Always limit depth and the number of paths.

### 65. Bidirectional BFS

**Definition:** Finding a shortest path by searching from both endpoints at once until the two searches meet.

**How it works:**
1. Run BFS forward from the source and backward from the target (following reversed edges).
2. Each step, expand whichever frontier is smaller.
3. When a node is reached by both searches, a path has been found. Finish the current level to make sure it's the shortest.
4. Join the two half-paths.
5. Each side explores only about half the depth, which is dramatically less work than one-sided BFS.

**Agent use:**
- **Role:** Retriever.
- **How:** Answers "how is X connected to Y?" quickly, even in large graphs. Useful for explanation ("why are these related?").
- **Rules:** Restrict edge types to meaningful relations. A path through generic hubs ("both are in the USA") explains nothing.
- **Guardrails:** Cap the depth and the visited nodes on both sides.

### 66. Dijkstra's algorithm

**Definition:** Finding the lowest-cost paths from a start node in a graph with non-negative edge weights.

**How it works:**
1. Give the start node distance 0 and every other node infinity.
2. Put the start node in a priority queue ordered by distance.
3. Remove the node with the smallest distance. Its distance is now final.
4. For each neighbor, if (this distance + edge weight) is smaller than the neighbor's current distance, update it and record the predecessor (relaxation).
5. Repeat until the target is finalized or the queue is empty.

**Agent use:**
- **Role:** Retriever.
- **How:** Used when edges have costs: lower confidence means a higher cost, longer distance, higher risk. It finds the "most reliable" or "cheapest" connection, not just the shortest.
- **Rules:** Define weights explicitly, for example cost = −log(confidence), so the path cost reflects combined confidence.
- **Guardrails:** Negative weights break Dijkstra. Validate that all weights are non-negative.

### 67. A* search

**Definition:** Dijkstra guided by a heuristic estimate of the remaining distance to the target.

**How it works:**
1. The priority is f(n) = g(n) + h(n): the cost so far plus the estimated cost to the target.
2. If h never overestimates (it's admissible), A* finds the optimal path.
3. A good heuristic focuses the search toward the target and expands far fewer nodes than Dijkstra.
4. Typical heuristics: geographic distance for spatial graphs, or distances to precomputed landmarks (the ALT method).

**Agent use:**
- **Role:** Retriever.
- **How:** Useful for spatial knowledge graphs (locations, routes) and big graphs with landmark-based estimates.
- **Rules:** Only use heuristics that are proven admissible when optimality matters.
- **Guardrails:** None specific beyond depth and visit caps.

### 68. Yen's k-shortest paths

**Definition:** Finding the k best simple paths (without repeated nodes) between two nodes, not just the best one.

**How it works:**
1. Find the shortest path (Dijkstra).
2. For each node along the current best path, temporarily block the edge used by earlier paths that share the same prefix, and find the shortest detour from that node to the target.
3. Prefix plus detour becomes a candidate path.
4. The best candidate becomes the next path in the list.
5. Repeat until k paths are found.

**Agent use:**
- **Role:** Retriever.
- **How:** Gives several alternative explanations of how two entities are connected. Better grounding for LLM answers than a single path (#158).
- **Rules:** Keep k small (3–10) and rank paths by meaningfulness, not just length.
- **Guardrails:** Cost grows with k and path length. Set timeouts.

### 69. Random walk with restart

**Definition:** Simulating random moves through the graph that jump back to the start node with some probability, to measure relevance to that start node.

**How it works:**
1. Start at the seed node.
2. At each step, with probability α, jump back to the seed. Otherwise move to a random neighbor (optionally weighted by edge type or weight).
3. Count how often each node is visited.
4. Visit frequencies converge to proximity scores relative to the seed. This is the same as personalized PageRank (#75).
5. Monte Carlo versions run many short walks in parallel.

**Agent use:**
- **Role:** Retriever.
- **How:** Ranks the entities around a seed by relevance, considering many paths, not just the shortest. That's useful for picking which facts to put into the LLM context.
- **Rules:** Use edge-type weights that reflect what matters for the task.
- **Guardrails:** Hubs attract walks. Down-weight or exclude generic hub nodes (#180).

### 70. Metapath-constrained traversal

**Definition:** Traversing only along a specific sequence of node and edge types, such as Author → Paper → Venue.

**How it works:**
1. Define a metapath: a typed sequence like `Person -worksFor-> Org -locatedIn-> City`.
2. Traverse step by step, following only edges of the expected type, to nodes of the expected type.
3. Count or score the paths matching the metapath between entities.
4. Different metapaths express different kinds of relatedness (colleagues versus co-authors).

**Agent use:**
- **Role:** Retriever.
- **How:** The agent defines meaningful metapaths for each question type, so retrieval explores relevant connections instead of everything nearby.
- **Rules:** Maintain a library of reviewed metapaths per use case.
- **Guardrails:** None specific beyond the usual caps.

### 71. Reachability indexes (2-hop labeling)

**Definition:** Precomputed labels that answer "can node A reach node B?" without a traversal.

**How it works:**
1. Pick hub nodes. For each node, store L_out (hubs it can reach) and L_in (hubs that can reach it).
2. A reaches B exactly when L_out(A) and L_in(B) share a hub.
3. Answering a query is a set intersection, which is fast.
4. Building good labels is computationally hard in general, so heuristics are used (ordering by degree, pruned landmark labeling).
5. Updates may require partial relabeling.

**Agent use:**
- **Role:** Retriever and Reasoner.
- **How:** Instant answers to "is X a descendant, dependency or subsidiary of Y?" on large hierarchies, which access-control checks often need.
- **Rules:** Rebuild or update the labels after structural changes.
- **Guardrails:** A stale index gives wrong answers. Check its version against the graph.

### 72. Transitive closure

**Definition:** Computing every pair (A, B) where B is reachable from A through some relation, such as all ancestors or all sub-parts.

**How it works:**
1. Repeatedly apply: if (A, B) and (B, C) are present, add (A, C), until nothing new appears (a fixpoint).
2. Efficient versions use semi-naive evaluation (#89): only join newly added pairs.
3. For DAGs, process in topological order. For general graphs, compute strongly connected components first (#80) and collapse them.
4. Store the results as materialized edges, or compute them at query time (#90).

**Agent use:**
- **Role:** Reasoner.
- **How:** Materializing closure for frequently queried hierarchies (category trees, org charts) makes queries simple and fast.
- **Rules:** Materialized closure edges are marked as inferred (K2), and maintained incrementally (#91).
- **Guardrails:** Closure of a large dense relation can be enormous (n² pairs). Estimate the size before materializing.

## B3. Centrality and community detection

### 73. Degree centrality

**Definition:** Ranking nodes by their number of connections.

**How it works:**
1. Count each node's edges: in-degree, out-degree or total, optionally per edge type.
2. Optionally normalize by the maximum possible degree.
3. The degree distribution of real graphs is usually heavily skewed: a few nodes have huge degrees.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** A quick importance signal, and the main way to detect supernodes (#180) that need special handling in traversals.
- **Rules:** Track the degree distribution over time (#189).
- **Guardrails:** High degree doesn't mean high importance. Generic nodes ("United States") have huge degree but little information for most questions.

### 74. PageRank

**Definition:** Ranking nodes by importance, where a node is important if important nodes point to it.

**How it works:**
1. Give every node equal initial rank.
2. Each iteration: each node shares its rank equally among its outgoing edges, and each node's new rank = (1 − d)/N + d × (sum of shares received). d is the damping factor, typically 0.85.
3. Nodes with no outgoing edges spread their rank evenly to all nodes.
4. Repeat until ranks change less than a tolerance.
5. Equivalent to the long-run visit frequency of a random surfer who sometimes jumps to a random node.

**Agent use:**
- **Role:** Retriever and Observer.
- **How:** A global importance prior for ranking entities in search and entity linking (#27), and for choosing which entities get descriptions or summaries first.
- **Rules:** Compute it on a snapshot (#14), and record the snapshot version.
- **Guardrails:** Link spam and duplicate entities distort scores. Clean the data first.

### 75. Personalized PageRank (PPR)

**Definition:** PageRank where the random jumps return to a chosen set of seed nodes, measuring importance relative to those seeds.

**How it works:**
1. Same as PageRank, except the teleport step goes to the seed nodes (for example the entities found in a question), not to random nodes.
2. Scores then reflect proximity and importance relative to the seeds.
3. Fast approximations: the push algorithm (local updates around the seeds) and Monte Carlo walks (#69).
4. Only the neighborhood of the seeds needs to be touched.

**Agent use:**
- **Role:** Retriever.
- **How:** One of the best ways to select a relevant subgraph for a question. Several GraphRAG approaches use PPR from the question's entities to rank facts and passages (#157).
- **Rules:** Seeds come from entity linking of the query (#154). Weight edges by relevance.
- **Guardrails:** Limit the number of nodes touched and the iterations, for predictable latency.

### 76. Betweenness centrality (Brandes' algorithm)

**Definition:** Ranking nodes by how often they lie on shortest paths between other nodes: the bridges and brokers.

**How it works:**
1. For each source node, run BFS (or Dijkstra) to find shortest paths and count how many shortest paths reach each node.
2. Walk back from the farthest nodes, accumulating each node's "dependency": the share of shortest paths through it.
3. Sum the dependencies over all sources.
4. The exact computation costs O(V × E). Sampling a subset of sources gives an approximation.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** Finds key connectors: people linking teams, systems linking services, accounts linking fraud clusters.
- **Rules:** Use sampled approximation on large graphs, and state the sample size.
- **Guardrails:** Expensive. Run it as a batch analytic job, never inside an interactive query.

### 77. Closeness and harmonic centrality

**Definition:** Ranking nodes by how close they are, on average, to all others.

**How it works:**
1. **Closeness:** 1 / (sum of shortest-path distances to all other nodes).
2. **Harmonic:** the sum of 1/distance over all other nodes. This handles disconnected graphs, since unreachable nodes contribute 0.
3. Computing it needs shortest paths from each node. Approximations use sampling or sketches (HyperLogLog-based methods such as HyperBall).

**Agent use:**
- **Role:** Observer.
- **How:** Identifies nodes that can reach everything quickly, such as central documents or core services.
- **Rules:** Prefer harmonic centrality for real graphs, which are often disconnected.
- **Guardrails:** Batch only on large graphs.

### 78. HITS and eigenvector centrality

**Definition:** Importance measures based on the principal eigenvector of the graph. HITS separates "hubs" (pointing to good authorities) from "authorities" (pointed to by good hubs).

**How it works:**
1. **Eigenvector centrality:** a node's score is proportional to the sum of its neighbors' scores. Compute it by power iteration.
2. **HITS:** keep two scores. Authority = sum of the hub scores of nodes pointing to it. Hub = sum of the authority scores of nodes it points to.
3. Alternate the updates and normalize until they converge.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** HITS fits directed graphs where "lists" and "referenced items" differ: curated index pages (hubs) versus authoritative documents (authorities).
- **Rules:** Run on topic-focused subgraphs for meaningful results.
- **Guardrails:** Easily distorted by densely interlinked clusters. Combine with other signals.

### 79. Connected components (union-find)

**Definition:** Grouping nodes into sets where every node can reach every other through edges, ignoring direction.

**How it works:**
1. Start with every node in its own set.
2. For each edge, union the sets of its two endpoints.
3. Union-find makes this nearly constant time per operation, using path compression (flattening chains during lookup) and union by rank (attaching the smaller tree under the larger).
4. At the end, each set is a component.
5. Parallel versions use label propagation of the minimum ID.

**Agent use:**
- **Role:** Curator and Observer.
- **How:** Used to group matched records into entities (#38), to find isolated islands in the graph (#190), and to split work into independent parts.
- **Rules:** Inspect unusually large components; they often reveal bad links.
- **Guardrails:** For entity resolution, components alone allow chain merges (#38). Add cluster-quality checks.

### 80. Strongly connected components (Tarjan / Kosaraju)

**Definition:** Groups of nodes in a directed graph where each node can reach every other node following edge directions.

**How it works:**
1. **Tarjan:** one DFS that tracks the earliest node reachable from each subtree ("lowlink"). When a node's lowlink equals its own index, pop its whole component off a stack.
2. **Kosaraju:** a DFS to get finish order, then a DFS on the reversed graph in decreasing finish order. Each tree found is one SCC.
3. Collapsing the SCCs gives a DAG (the condensation).

**Agent use:**
- **Role:** Reasoner and Observer.
- **How:** Detects cycles where there shouldn't be any (circular ownership, cyclic category hierarchies, circular dependencies), which usually means data errors.
- **Rules:** Relations declared acyclic in the schema (`subClassOf`, `partOf`) are checked for SCCs larger than one node.
- **Guardrails:** Report cycles for review rather than breaking them automatically.

### 81. Louvain community detection

**Definition:** Finding groups of densely connected nodes by greedily maximizing modularity.

**How it works:**
1. Modularity measures how many edges fall within communities, compared to what random wiring would give.
2. **Phase 1:** start with each node in its own community. Move each node to the neighboring community giving the biggest modularity gain. Repeat until no move helps.
3. **Phase 2:** collapse each community into a single node (summing edge weights) and repeat phase 1 on the smaller graph.
4. Continue until modularity stops improving. The result is a hierarchy of communities.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** Groups entities into topics or clusters, which is the basis for GraphRAG community summaries (#155).
- **Rules:** Use Leiden (#82) when community quality matters.
- **Guardrails:** Louvain can produce badly connected or even disconnected communities. Check them.

### 82. Leiden community detection

**Definition:** An improvement on Louvain that guarantees well-connected communities.

**How it works:**
1. Like Louvain: local node moves, then aggregation.
2. Adds a refinement phase between them: within each community, nodes are re-clustered into well-connected sub-communities, and aggregation is based on those.
3. This prevents the disconnected communities Louvain can produce, and usually reaches better quality.
4. A resolution parameter controls community size: higher means more, smaller communities.
5. Hierarchical runs give communities at several levels.

**Agent use:**
- **Role:** Retriever and Operator.
- **How:** The usual choice for GraphRAG (#155): communities at several levels are each summarized by an LLM, supporting global "what are the main themes?" questions.
- **Rules:** Record the resolution, seed and graph version. Different settings give different communities.
- **Guardrails:** Communities change as the graph changes, so summaries must be refreshed (#176).

### 83. Label propagation

**Definition:** A fast community-detection (or classification) method where nodes repeatedly adopt their neighbors' most common label.

**How it works:**
1. Give each node a unique label (for communities), or seed some nodes with known labels (for classification).
2. In each round, every node adopts the label most common among its neighbors (weighted, ties broken randomly).
3. Repeat until labels stop changing.
4. Nodes with the same label form a community or class.
5. Near-linear time and easy to parallelize.

**Agent use:**
- **Role:** Observer and Curator.
- **How:** Quick clustering on very large graphs, and spreading known labels (such as "fraud" or "topic X") to nearby unlabeled nodes.
- **Rules:** Results vary between runs. Fix the random seed or combine several runs.
- **Guardrails:** Propagated labels are inferred (K2). Never treat a propagated "fraud" label as a confirmed fact.

### 84. k-core decomposition

**Definition:** Finding nested subgraphs where every node has at least k connections within the subgraph.

**How it works:**
1. Repeatedly remove nodes with degree below k, updating their neighbors' degrees.
2. What remains is the k-core.
3. Doing this for increasing k gives each node a core number (the largest k-core it belongs to).
4. It runs in linear time with bucket-based degree tracking.
5. High core numbers mark the densely connected center of the graph.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** Finds the dense core of a domain, and helps filter noise: low-core nodes are peripheral. Also used to detect dense suspicious groups.
- **Rules:** Use core numbers as features, not as truth.
- **Guardrails:** None specific.

## B4. Reasoning

### 85. RDFS entailment rules

**Definition:** The standard inference rules that derive new triples from RDFS schema statements.

**How it works:**
1. **Subclass:** (x type A) and (A subClassOf B) gives (x type B).
2. **Subproperty:** (x p y) and (p subPropertyOf q) gives (x q y).
3. **Domain:** (x p y) and (p domain C) gives (x type C). **Range:** (x p y) and (p range C) gives (y type C).
4. Transitivity of `subClassOf` and `subPropertyOf`.
5. Apply the rules until nothing new is derived (a fixpoint).

**Agent use:**
- **Role:** Reasoner.
- **How:** Lets queries find everything of a type, including subtypes, without listing them all.
- **Rules:** Inferred triples are stored separately or marked (K2), so they're never confused with asserted facts.
- **Guardrails:** Wrong domain and range statements produce many wrong types. Watch for sudden type-count jumps after schema changes.

### 86. OWL 2 RL rule-based reasoning

**Definition:** The OWL 2 profile designed to be implemented with rules, which scales to large data.

**How it works:**
1. OWL 2 RL defines a fixed set of rules covering much of OWL: inverse, symmetric and transitive properties, `sameAs`, functional properties, class intersections, and more.
2. A rule engine (forward chaining, #87) applies them to the data until a fixpoint.
3. Some rules detect inconsistency (an individual in two disjoint classes) instead of deriving facts.
4. The runtime is polynomial in the data size.

**Agent use:**
- **Role:** Reasoner.
- **How:** The practical choice for reasoning over large instance graphs: inverse relations, transitive part-of, and inconsistency detection.
- **Rules:** Keep the ontology within OWL 2 RL when using rule engines.
- **Guardrails:** `owl:sameAs` and functional properties can trigger huge equality chains (#92). Monitor the inferred-fact counts.

### 87. Forward chaining with the Rete algorithm

**Definition:** Applying rules to data proactively, deriving every consequence and storing it, using an efficient match network (Rete).

**How it works:**
1. Compile the rules into a network: alpha nodes test single conditions; beta nodes join conditions together.
2. Facts flow through the network. Partial matches are remembered at each node.
3. When a rule's conditions are fully matched, it fires and adds new facts, which flow through the network too.
4. Only changes are processed (incremental), so adding one fact doesn't re-evaluate everything.
5. Memory grows with the number of partial matches.

**Agent use:**
- **Role:** Reasoner.
- **How:** Good for continuously updated graphs where derived facts must be available immediately (alerts, compliance rules).
- **Rules:** Each rule has an ID, an owner and tests. Derived facts record which rule produced them (K1).
- **Guardrails:** Rules that create new entities can loop forever. Test termination, and set limits on derived facts per run.

### 88. Backward chaining (goal-driven reasoning)

**Definition:** Starting from a question (goal) and working backward through rules to find supporting facts.

**How it works:**
1. Take the goal, for example "is X an ancestor of Y?".
2. Find rules whose conclusion matches the goal.
3. Their conditions become sub-goals. Prove them recursively against stored facts or other rules (SLD resolution, as in Prolog).
4. Succeed when all sub-goals are proven. Otherwise try other rules.
5. Tabling (memoizing sub-goals) prevents infinite loops on recursive rules.

**Agent use:**
- **Role:** Reasoner and Retriever.
- **How:** Suitable when inferences are needed rarely, or when storing every inferred fact would be too large: reason only about what's asked.
- **Rules:** Use tabling for recursive rules.
- **Guardrails:** Set depth limits and timeouts per query.

### 89. Datalog with semi-naive evaluation

**Definition:** A logic rule language (recursive, without functions) evaluated efficiently by only processing new facts each round.

**How it works:**
1. Rules look like `ancestor(X,Z) :- parent(X,Y), ancestor(Y,Z).`
2. **Naive evaluation:** re-apply all rules to all facts each round until nothing changes. Very redundant.
3. **Semi-naive:** each round, join only with the facts that were new in the previous round (the delta), because older combinations were already tried.
4. Stop when a round produces no new facts.
5. Stratification handles negation safely: evaluate the negated relations completely before using them.

**Agent use:**
- **Role:** Reasoner.
- **How:** A clean, predictable rule engine for custom business inference: access inheritance, ownership chains, compliance derivations.
- **Rules:** Rules are versioned and tested on example facts with expected outputs.
- **Guardrails:** Estimate the output size of recursive rules before running them on full data.

### 90. Materialization versus query-time reasoning

**Definition:** Choosing whether to compute and store inferred facts ahead of time, or to compute them on demand during queries.

**How it works:**
1. **Materialization:** run the reasoner and store all inferences. Queries are fast and simple. It costs storage and must be maintained on updates (#91).
2. **Query-time:** rewrite queries (#60) or backward-chain (#88) when queried. Always current and uses no extra storage, but queries are slower and more complex.
3. **Hybrid:** materialize stable, frequently used inferences (hierarchies), and compute volatile or rare ones on demand.

**Agent use:**
- **Role:** Operator and Reasoner.
- **How:** The agent picks per rule set by query frequency, update frequency and inference volume.
- **Rules:** Document which inferences are materialized and when they were last updated.
- **Guardrails:** Stale materialized inferences give wrong answers. Monitor the reasoning lag after updates.

### 91. Incremental maintenance of inferences (DRed)

**Definition:** Updating materialized inferences when facts are added or deleted, without recomputing everything.

**How it works:**
1. **Additions:** run semi-naive evaluation starting from the new facts only.
2. **Deletions (Delete-and-Rederive):**
   - Over-delete: remove every inferred fact that depended on the deleted fact, even if it might have other support.
   - Re-derive: for each over-deleted fact, check whether it can still be derived from the remaining facts, and put it back if so.
3. Alternative: counting-based methods track how many derivations support each fact, and delete it when the count reaches zero.

**Agent use:**
- **Role:** Reasoner.
- **How:** Keeps inferred facts correct as the graph changes, which is critical when facts get retracted (corrections, deletions).
- **Rules:** Every deletion of asserted facts triggers inference maintenance.
- **Guardrails:** Inferred facts that outlive their deleted source facts violate deletion requests (KG2). Verify after deletions.

### 92. Equality reasoning (owl:sameAs handling)

**Definition:** Handling statements that two identifiers denote the same entity, without exploding the number of triples.

**How it works:**
1. `sameAs` is symmetric and transitive, and every fact about one identifier applies to all its equivalents.
2. Naive materialization copies every fact to every equivalent identifier, which is quadratic and explosive.
3. **Rewriting:** pick one representative per equivalence class (with union-find, #79), and rewrite all facts to use it.
4. Keep the mapping from all aliases to the representative, for lookup and display.
5. Undoing a wrong `sameAs` means splitting the class and restoring the original facts.

**Agent use:**
- **Role:** Reasoner and Curator.
- **How:** The agent treats equality as entity resolution (#38–39): one representative per entity, with alias lists.
- **Rules:** Only assert equality with strong evidence (K7).
- **Guardrails:** A single wrong `sameAs` between two big entities corrupts both. Equivalence classes above a size threshold get reviewed (KG3).

### 93. Description logics and tableau reasoning

**Definition:** The formal logic family behind OWL, with tableau algorithms that decide satisfiability, subsumption and consistency.

**How it works:**
1. A TBox holds concept definitions and axioms (`Parent ≡ Person ⊓ ∃hasChild.Person`). An ABox holds facts about individuals.
2. Reasoning tasks: is a concept satisfiable? Is A a subclass of B? Is the ABox consistent with the TBox? Which individuals are instances of a concept?
3. **Tableau:** to check whether a statement holds, try to build a model of its negation. Apply expansion rules (∃ creates a new individual, ⊔ branches into alternatives). If every branch reaches a contradiction (a clash), the statement holds.
4. Blocking prevents infinite expansion with cyclic definitions.
5. Expressive logics are computationally expensive in the worst case.

**Agent use:**
- **Role:** Reasoner (ontology design).
- **How:** Used to check ontology quality before deployment: unsatisfiable classes (classes that can never have members) reveal modeling errors.
- **Rules:** Run full DL reasoning on the ontology (TBox), and lighter profiles on big instance data.
- **Guardrails:** Don't run expressive DL reasoners over millions of instances on the request path.

### 94. OWL 2 EL classification (consequence-based reasoning)

**Definition:** Fast computation of the full class hierarchy for large ontologies using the OWL 2 EL profile.

**How it works:**
1. OWL 2 EL allows conjunctions and existential restrictions, but not universal restrictions or disjunctions.
2. Consequence-based reasoners apply completion rules that derive subsumptions directly (A ⊑ B, A ⊑ ∃r.B).
3. The rules run in polynomial time, even for hundreds of thousands of classes.
4. Output: the complete inferred class hierarchy.

**Agent use:**
- **Role:** Reasoner.
- **How:** Used for large terminologies (medical, product or industry classifications), where the hierarchy must be complete and correct.
- **Rules:** Re-classify after every ontology change, and compare against the previous hierarchy.
- **Guardrails:** Unexpected new subsumptions after a change often signal modeling errors. Review the differences.

### 95. Rule mining (AMIE-style)

**Definition:** Automatically discovering logical rules that hold frequently in a knowledge graph.

**How it works:**
1. Search for candidate Horn rules such as `livesIn(X,Y) ⇐ marriedTo(X,Z), livesIn(Z,Y)`, by refining rules step by step (adding atoms).
2. **Support:** how many facts the rule correctly predicts.
3. **Confidence:** support divided by the number of predictions. **PCA confidence** counts only predictions where the subject has some known value for the relation, compensating for the open world (#96).
4. Keep rules above support and confidence thresholds.
5. Mined rules can predict missing facts or flag anomalies.

**Agent use:**
- **Role:** Reasoner and Observer.
- **How:** Finds regularities and likely gaps. Predicted facts become candidates for completion (#132).
- **Rules:** Mined rules are proposals (K7). Predicted facts are marked inferred, with the rule and its confidence.
- **Guardrails:** Rules learned from biased data reproduce the bias. Review rules before using them in decisions.

### 96. Open-world versus closed-world assumption

**Definition:** Whether missing information means "unknown" (open world) or "false" (closed world).

**How it works:**
1. **Open world (RDF, OWL):** a missing fact isn't false; it may just be unrecorded. "Does Alice have children?" with no data means "unknown".
2. **Closed world (databases, SHACL, most applications):** if it isn't recorded, it's treated as false.
3. Consequences: OWL can't flag a missing required property as an error (SHACL does). Negation and counting queries depend heavily on this choice.
4. Many real systems mix them: the closed world for complete, authoritative data, the open world for extracted knowledge.

**Agent use:**
- **Role:** Retriever and Reasoner.
- **How:** The agent answers "no" only when the data for that relation is known to be complete. Otherwise it says "not found in the knowledge graph".
- **Rules:** Mark which relations and sources are considered complete.
- **Guardrails:** Never turn "absent from the graph" into a negative factual claim for incomplete data.

### 97. Inconsistency detection and explanation (justifications)

**Definition:** Finding facts and axioms that contradict each other, and the minimal set of statements that causes each contradiction.

**How it works:**
1. Detection: a reasoner finds clashes, such as an individual in disjoint classes, a functional property with two different values, or a violated constraint.
2. **Justification:** a minimal set of axioms and facts that together produce the problem.
3. To find one, start from all relevant statements and remove statements one at a time while the contradiction persists (black-box methods), or trace the reasoner's derivation.
4. Present justifications to people for repair (#100).

**Agent use:**
- **Role:** Reasoner and Observer.
- **How:** The agent explains why the graph is inconsistent or why an inference was made, citing the exact facts involved, instead of a generic error.
- **Rules:** Run consistency checks after bulk loads and schema changes.
- **Guardrails:** An inconsistent graph makes classical reasoners derive anything. Block reasoning-based answers until the inconsistency is resolved or isolated.

### 98. Probabilistic logic (Markov logic networks, probabilistic soft logic)

**Definition:** Combining logical rules with probabilities, so rules can be soft and facts uncertain.

**How it works:**
1. Each rule gets a weight that reflects how strongly it tends to hold.
2. **MLN:** rule groundings define a probability distribution over possible worlds. More satisfied high-weight rules means a more likely world. Inference is by sampling or approximate methods.
3. **PSL:** truth values are continuous in [0, 1], and rules become convex penalties, so inference is a fast convex optimization.
4. The weights are learned from data.
5. Output: probabilities, or soft truth values, for uncertain facts.

**Agent use:**
- **Role:** Reasoner.
- **How:** Combines noisy extracted facts with soft rules ("people usually live where their employer is located") to estimate which facts are probably true, such as for entity resolution and truth discovery (#50).
- **Rules:** Store probabilities as confidence (K1). Never present them as certainties.
- **Guardrails:** Inference is expensive. Run it as a batch job, and limit grounding size.

### 99. Temporal reasoning (Allen's interval algebra)

**Definition:** Reasoning about how time intervals relate: before, meets, overlaps, during, starts, finishes, equals, and their inverses.

**How it works:**
1. Allen's interval algebra defines 13 basic relations between two intervals.
2. Facts with validity intervals (K8) can be compared: "did employment A overlap employment B?".
3. Composition tables infer the relation between A and C from the relations A–B and B–C.
4. Path consistency algorithms check that a set of temporal constraints doesn't contradict itself.
5. Point-based time (start and end timestamps) makes most checks simple comparisons.

**Agent use:**
- **Role:** Reasoner and Retriever.
- **How:** Answers time-sensitive questions correctly ("who was CEO when the acquisition happened?") and detects impossible timelines (a person employed after death).
- **Rules:** Store valid time as explicit start and end values, in a normalized form (#33).
- **Guardrails:** Open-ended intervals (an unknown end) must be handled explicitly. Don't treat a missing end as "still true" without evidence.

### 100. Inconsistency repair

**Definition:** Choosing which facts or axioms to remove or change to resolve contradictions, with minimal loss.

**How it works:**
1. Collect all justifications for the contradictions (#97).
2. A repair must remove at least one statement from every justification. Choosing the smallest such set is a minimal hitting set problem.
3. Prefer removing low-confidence, low-trust or extracted facts over trusted asserted facts and axioms.
4. Alternatively, mark facts as disputed instead of deleting them.
5. Check that the repair doesn't create new inconsistencies.

**Agent use:**
- **Role:** Curator and Reasoner.
- **How:** The agent proposes repairs ranked by confidence and source trust, with explanations. People approve repairs that touch trusted data.
- **Rules:** Repairs are recorded with their justification, and are reversible (KG6).
- **Guardrails:** Never auto-delete asserted facts from trusted sources. Downgrade or flag them, and escalate (KG3).
