# Part 4: Observability (#156–200)

## D1. Retrieval quality metrics

### 156. Recall@k (against exact ground truth)

**Definition:** The fraction of the true k nearest neighbors that the approximate index actually returned.

**How it works:**
1. For a sample of queries, compute the exact top k with brute force (#51). That's the ground truth.
2. Run the same queries through the production index with production parameters and filters.
3. For each query, recall@k = |returned ∩ true top k| / k.
4. Average over queries, and also look at the distribution: the worst 5% of queries matter.
5. Break it down by segment: tenant, filter selectivity, topic, data age.

**Agent use:**
- **Role:** Observer.
- **How:** This measures the index itself, separate from whether the embeddings are any good. The agent runs it on a schedule and before and after every index change (V5).
- **Rules:** Use the same filters as production when computing ground truth. Unfiltered recall can look fine while filtered recall is poor.
- **Guardrails:** Alert when recall drops below target overall or in any major segment.

### 157. Ground-truth sampling (shadow brute force)

**Definition:** Continuously computing exact results for a small sample of real queries, to monitor live recall.

**How it works:**
1. Sample a small percentage of production queries (privacy-reviewed, VG2).
2. Asynchronously run exact brute-force search for them, on a replica or offline copy at the same snapshot (#133).
3. Compare with what production returned (logged in the trace, #192).
4. Aggregate into a live recall metric over time.
5. Use the snapshot version so data changes don't count as errors.

**Agent use:**
- **Role:** Observer.
- **How:** Gives real-traffic recall, not just synthetic benchmark recall. Recall drift shows up quickly.
- **Rules:** Compare at the same snapshot version.
- **Guardrails:** Run brute force off the serving path (VG3), and keep sampled queries under the same retention and privacy rules as other logs.

### 158. Precision@k

**Definition:** The fraction of the top k results that are actually relevant to the query.

**How it works:**
1. Get relevance judgments for the returned results: human labels, LLM judges (#163), or clicks.
2. For each query, precision@k = (relevant results in top k) / k.
3. Average over queries.
4. Unlike recall@k (#156), this measures whether results are useful, not whether the index matched brute force.

**Agent use:**
- **Role:** Observer.
- **How:** Tells the agent whether filling the context with the top k adds noise. Low precision means retrieving fewer results or reranking more.
- **Rules:** Use it together with recall-type metrics; precision alone rewards returning very few results.
- **Guardrails:** Use consistent labeling guidelines, or the metric drifts with the labelers.

### 159. Mean Reciprocal Rank (MRR)

**Definition:** The average of 1 / (rank of the first relevant result) across queries.

**How it works:**
1. For each query, find the position of the first relevant result.
2. Its reciprocal rank is 1/position (1 if first, 0.5 if second, and so on), or 0 if none is in the list.
3. Average across queries.
4. It focuses on how quickly the first good answer appears.

**Agent use:**
- **Role:** Observer.
- **How:** Good for question-answering and lookup tasks where one correct passage is enough.
- **Rules:** Use a fixed cutoff (MRR@10), so values are comparable.
- **Guardrails:** It ignores everything after the first relevant result. Don't use it alone for tasks that need several sources.

### 160. nDCG (normalized discounted cumulative gain)

**Definition:** A ranking metric that rewards placing highly relevant results near the top, with graded relevance.

**How it works:**
1. Each result has a graded relevance (for example 0–3).
2. DCG = Σ (2^relevance − 1) / log₂(rank + 1). Lower positions are discounted.
3. Compute the ideal DCG: the best possible ordering of the known relevant results.
4. nDCG = DCG / ideal DCG, ranging from 0 to 1.
5. Average across queries at a cutoff (nDCG@10).

**Agent use:**
- **Role:** Observer.
- **How:** The standard metric for comparing retrieval configurations (models, fusion weights, rerankers) on a labeled set.
- **Rules:** Use graded labels where possible. Binary labels lose information.
- **Guardrails:** Unlabeled results count as non-relevant. When comparing a new system that surfaces new documents, label them first, or the new system is unfairly penalized.

### 161. Hit rate (success@k)

**Definition:** The fraction of queries where at least one relevant result appears in the top k.

**How it works:**
1. For each query, check whether any of the top k is relevant.
2. Count it as 1 or 0.
3. Average across queries.

**Agent use:**
- **Role:** Observer.
- **How:** The simplest health metric for RAG: did the retrieval give the model anything useful at all? A failed hit almost guarantees a bad or hallucinated answer.
- **Rules:** Track hit rate at the k the agent actually uses.
- **Guardrails:** Investigate queries with no hit as a group (#194). They often share a cause.

### 162. Relative distance error

**Definition:** How much worse the returned neighbors' distances are than the true neighbors' distances.

**How it works:**
1. For each query, compare the distance of the i-th returned result with the distance of the true i-th nearest neighbor.
2. Relative error = (returned distance − true distance) / true distance.
3. Average across positions and queries.
4. A missed neighbor that was replaced by an almost equally close one gives a small error, even though recall drops.

**Agent use:**
- **Role:** Observer.
- **How:** Complements recall. When many vectors are nearly tied, recall may look low while results are effectively just as good.
- **Rules:** Report it alongside recall@k.
- **Guardrails:** Don't use it to excuse low recall when exact items matter (deduplication, exact lookups).

### 163. LLM-as-judge relevance evaluation

**Definition:** Using a language model to label retrieved results as relevant or not, at scale.

**How it works:**
1. Give the model the query, a passage and a clear grading rubric (for example 0–3 relevance with definitions).
2. Ask for a grade and a short justification.
3. Calibrate against human labels on a sample: measure agreement (for example Cohen's κ).
4. Use the judge for large-scale evaluation, and keep spot-checking with humans.

**Agent use:**
- **Role:** Observer.
- **How:** Lets the agent evaluate retrieval changes on thousands of queries without waiting for human labels.
- **Rules:** The judge model, prompt and rubric are versioned. Changing any of them changes the metric.
- **Guardrails:** Judges have biases: favoring long passages, or text that sounds like their own output. Check agreement with humans regularly, and treat retrieved passages as data, not instructions (VG6).

### 164. Golden query set regression testing

**Definition:** A fixed, curated set of queries with known relevant results, run against every retrieval change.

**How it works:**
1. Collect representative queries: common ones, hard ones, known past failures, and each important segment.
2. Label the relevant results for each.
3. Before any change (model, chunking, index parameters, fusion weights), run the set on both old and new configurations.
4. Compare the metrics (nDCG, hit rate, recall) overall and per query.
5. Block changes that regress beyond a tolerance, and review the queries that got worse.

**Agent use:**
- **Role:** Observer and Operator.
- **How:** The agent's main safety gate for retrieval changes (V5). Each production failure becomes a new golden query.
- **Rules:** Version the golden set, and keep it in sync with corpus changes (the relevant documents must still exist).
- **Guardrails:** Never tune on the golden set alone. Keep a held-out part to avoid overfitting.

### 165. Online implicit feedback

**Definition:** Learning about retrieval quality from user behavior: clicks, citations used, follow-up questions, "thumbs down".

**How it works:**
1. Log what was retrieved and shown, and what the user did next.
2. Positive signals: a result clicked or opened, an answer accepted, a source cited.
3. Negative signals: a rephrased query right away, a thumbs down, a quick abandonment.
4. Aggregate per query type and over time.
5. Correct for position bias: top results get clicked more simply because they're on top.

**Agent use:**
- **Role:** Observer.
- **How:** Shows real-world quality trends and supplies hard examples for golden sets (#164) and hard-negative mining (#8).
- **Rules:** Treat implicit signals as noisy. Use them for trends and candidate selection, not as ground truth.
- **Guardrails:** Logging user behavior follows privacy rules (VG2): anonymize, sample, and set retention limits.

### 166. Interleaving experiments

**Definition:** Comparing two rankers by merging their results into one list and seeing which one's results users prefer.

**How it works:**
1. For each query, run rankers A and B.
2. Merge them with team-draft interleaving: take turns picking each ranker's best not-yet-chosen result, recording which ranker contributed each item.
3. Show the merged list.
4. Credit clicks to the contributing ranker.
5. Over many queries, the ranker with more credited clicks wins. This needs far fewer queries than an A/B test.

**Agent use:**
- **Role:** Observer and Operator.
- **How:** A sensitive way to test retrieval changes on live traffic. For agent pipelines, "click" can be "passage cited in the final answer".
- **Rules:** Run only after offline checks (#164) pass.
- **Guardrails:** Both rankers must respect the same access filters (VG1).

### 167. Faithfulness and groundedness (RAG evaluation)

**Definition:** Whether a generated answer is actually supported by the retrieved passages.

**How it works:**
1. Split the answer into individual claims.
2. For each claim, check whether some retrieved passage supports it, with a judge model (#163) or an entailment classifier.
3. Faithfulness = supported claims / all claims.
4. Also measure answer relevance (does it answer the question?) and context relevance (#158).
5. Low faithfulness with good retrieval means a generation problem; low faithfulness with poor retrieval means a retrieval problem.

**Agent use:**
- **Role:** Observer.
- **How:** Separates retrieval failures from generation failures, so the agent fixes the right component.
- **Rules:** Store the retrieved passages with each answer (#192), so faithfulness can be checked later.
- **Guardrails:** Unsupported claims in high-stakes answers are flagged before delivery, or the answer states its uncertainty.

## D2. Embedding drift and distribution monitoring

### 168. Centroid shift

**Definition:** Measuring how far the average embedding (or the cluster centers) of new data has moved from a reference period.

**How it works:**
1. Compute the mean vector of a reference window (for example the training or indexing period).
2. Compute the mean vector of the current window.
3. Measure the distance between them (cosine or L2).
4. Do the same per cluster: track how far new vectors land from their nearest centroid.
5. A rising distance means the new content differs from what the index was built on.

**Agent use:**
- **Role:** Observer.
- **How:** An early, cheap signal that quantizers, centroids or even the embedding model may no longer fit the data (#120, #153).
- **Rules:** Use fixed reference windows, and compare like with like (same sources, same languages).
- **Guardrails:** Shift isn't automatically bad (new product lines). Combine it with quality metrics before acting.

### 169. Maximum Mean Discrepancy (MMD)

**Definition:** A statistical test for whether two sets of vectors come from the same distribution.

**How it works:**
1. Choose a kernel (often Gaussian) measuring similarity between vectors.
2. MMD² = average within-set-A similarity + average within-set-B similarity − 2 × average cross-set similarity.
3. If A and B come from the same distribution, MMD is near zero.
4. Get significance with a permutation test: shuffle the set labels many times and see how often MMD is that large by chance.
5. It captures differences in shape, not just in the mean.

**Agent use:**
- **Role:** Observer.
- **How:** A principled drift detector for embeddings, comparing this week's document or query vectors with a reference sample.
- **Rules:** Use fixed sample sizes and a fixed kernel width, so results are comparable over time.
- **Guardrails:** Large samples make tiny, irrelevant differences "significant". Track effect size, not just p-values.

### 170. PSI and KS tests on projections

**Definition:** Detecting drift by comparing the distributions of individual projected dimensions between periods.

**How it works:**
1. Project vectors onto a few fixed directions, such as the top principal components from a reference period (#23).
2. For each direction, compare the reference and current distributions.
3. **KS test:** the maximum gap between the two cumulative distributions.
4. **PSI (population stability index):** bin both distributions, then sum (current% − reference%) × ln(current% / reference%). Common rule of thumb: 0.1 = minor shift, 0.25 = major shift.
5. Report which directions drifted.

**Agent use:**
- **Role:** Observer.
- **How:** Simple, interpretable drift dashboards. Drift along a specific component can be traced to the content that changed.
- **Rules:** Freeze the projection directions. Recomputing them every period hides drift.
- **Guardrails:** Correct for many simultaneous tests, or random alarms appear.

### 171. Similarity score distribution monitoring

**Definition:** Tracking the distribution of retrieval scores (for example the top-1 and top-k cosine scores) over time.

**How it works:**
1. For every query (or a sample), log the scores of the returned results.
2. Track percentiles over time: median top-1 score, k-th score, and the gap between them.
3. Falling top-1 scores mean queries find weaker matches: missing content, drift or index problems.
4. Scores bunching together means poor separation (anisotropy, #16) or a broken model.
5. Compare by segment (tenant, query type).

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** A cheap continuous signal with no labels needed. A sudden shift often reveals a deployment bug (a wrong model or missing prefix, #6) immediately.
- **Rules:** Alert on sudden distribution shifts, not only on slow trends.
- **Guardrails:** Scores are only comparable within one model and configuration (V2). Reset the baselines after a model change.

### 172. Vector norm distribution

**Definition:** Monitoring the lengths of the vectors being written and queried.

**How it works:**
1. Compute the L2 norm of each new vector (before normalization, if normalization happens later).
2. Track the norm distribution: mean, percentiles, and counts of zero or NaN vectors.
3. Normalized pipelines should produce vectors of length 1. Deviations mean a bug.
4. Unexpected norms reveal empty inputs, truncation, wrong pooling or a model change.

**Agent use:**
- **Role:** Observer and Transformer.
- **How:** A fast integrity check on the embedding pipeline. The agent rejects bad vectors (NaN, zero, unexpected norms) at write time.
- **Rules:** Validate every vector before writing: correct dimension, finite values, expected norm range.
- **Guardrails:** Never write NaN or zero vectors. They can break distance calculations or become hubs.

### 173. Partition and cluster balance

**Definition:** Measuring how evenly vectors are spread across IVF lists, partitions or shards.

**How it works:**
1. Count the vectors per list or partition.
2. Compute imbalance measures: the coefficient of variation (standard deviation / mean), the Gini coefficient, or max / mean.
3. Also track query-weighted load: how often each list is probed.
4. Highly unbalanced lists make some queries much slower and can lower recall.

**Agent use:**
- **Role:** Observer.
- **How:** Triggers centroid retraining (#120) or rebalancing (#139) before latency suffers.
- **Rules:** Track imbalance at build time as a baseline, then over time.
- **Guardrails:** Alert on lists far above the average size, since they dominate tail latency.

### 174. Hubness measurement (k-occurrence skew)

**Definition:** Measuring how unevenly vectors appear in other vectors' nearest-neighbor lists.

**How it works:**
1. For a sample of vectors (or queries), compute their top-k neighbors.
2. Count, for each vector, how often it appears in those lists (its k-occurrence).
3. Compute the skewness of the k-occurrence distribution. High skew means a few hubs appear everywhere.
4. List the top hubs and inspect them.

**Agent use:**
- **Role:** Observer.
- **How:** Identifies documents that pollute many results (boilerplate, very generic text, broken vectors). The agent fixes them by removing boilerplate at chunking, applying hubness correction (#21), or filtering.
- **Rules:** Inspect the top hubs regularly.
- **Guardrails:** Some hubs are legitimately central documents. Confirm before suppressing them.

### 175. Intrinsic dimensionality estimation

**Definition:** Estimating how many dimensions the data really uses, regardless of the vector length.

**How it works:**
1. **Local method (maximum likelihood, TwoNN):** for each point, look at the ratio between its distances to its first and second nearest neighbors.
2. The way these ratios are distributed reveals the local dimension.
3. Average over points to get a global estimate.
4. **PCA alternative:** count how many components explain, say, 95% of variance (#23).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** Guides how far dimension reduction or Matryoshka truncation (#9, #23) can safely go, and explains search difficulty: higher intrinsic dimension makes ANN harder.
- **Rules:** Use it as guidance, then confirm with recall measurements.
- **Guardrails:** None specific.

### 176. Outlier detection on embeddings

**Definition:** Finding vectors that are unusual compared to the rest of the corpus.

**How it works:**
1. **k-NN distance:** points far from their k nearest neighbors are outliers.
2. **LOF (local outlier factor):** compares a point's local density with its neighbors' densities.
3. **Isolation forest:** random splits isolate outliers in fewer steps.
4. Score every new vector, and flag those above a threshold.

**Agent use:**
- **Role:** Observer and Transformer.
- **How:** Catches broken inputs (garbled text, binary data, extraction failures), spam and content in unexpected languages, at ingestion time.
- **Rules:** Quarantine flagged items for review, rather than deleting them automatically.
- **Guardrails:** Genuinely new topics look like outliers at first. Review before excluding.

### 177. Query out-of-distribution (OOD) detection

**Definition:** Detecting queries that fall outside what the corpus covers.

**How it works:**
1. Compare each query vector with the corpus: its distance to the nearest centroids, or its top-1 score (#171).
2. If it's far from all corpus regions, the query is out of distribution.
3. Track the OOD rate over time and cluster OOD queries to find content gaps.
4. Optionally use a classifier trained on in-domain and out-of-domain queries.

**Agent use:**
- **Role:** Retriever and Observer.
- **How:** When a query is OOD, the agent says the knowledge base doesn't cover it, instead of answering from weak matches. OOD clusters guide which content to add.
- **Rules:** Use calibrated thresholds (#20).
- **Guardrails:** Never fill the context with low-relevance results just because k results were requested.

## D3. System metrics and SLOs

### 178. Latency histograms and percentiles

**Definition:** Recording the distribution of request latency, and reporting percentiles (p50, p95, p99), not averages.

**How it works:**
1. Record each request's duration into a histogram with fixed or exponential buckets (Prometheus histograms, OpenTelemetry metrics).
2. Compute percentiles from the histogram: p50 (typical), p95 and p99 (tail).
3. Break it down by stage: embedding the query, ANN search, filtering, re-scoring, reranking, network.
4. Averages hide tail problems. One slow shard or disk shows up only in p99.

**Agent use:**
- **Role:** Observer.
- **How:** The agent sees which stage dominates latency and tunes that stage (ef, re-score factor, reranker size) rather than guessing.
- **Rules:** Always report per-stage latency percentiles.
- **Guardrails:** Never average percentiles across machines. Merge the histograms or sketches instead (#190).

### 179. RED and USE methods

**Definition:** Two checklists of core metrics. RED for services (Rate, Errors, Duration) and USE for resources (Utilization, Saturation, Errors).

**How it works:**
1. **RED per service:** requests per second, error rate, latency distribution (#178).
2. **USE per resource** (CPU, memory, disk, GPU, network): how busy it is, how much work is waiting (queues), and its error count.
3. A latency spike (RED) is traced to a saturated resource (USE).
4. Apply both to every component: embedding service, vector index, metadata store, reranker.

**Agent use:**
- **Role:** Observer.
- **How:** Gives the agent a systematic diagnosis path: start from the user-visible symptom (RED), then find the resource (USE).
- **Rules:** Every component exports both sets of metrics.
- **Guardrails:** Don't alert on raw utilization alone. High utilization without saturation is just efficient use.

### 180. SLOs and error-budget burn rate

**Definition:** Explicit targets for reliability (for example "99% of searches under 200 ms"), and alerts based on how fast the allowed failures are being used up.

**How it works:**
1. Define SLIs (what's measured: latency, availability, freshness, recall) and SLOs (targets over a window, such as 30 days).
2. Error budget = 1 − the SLO (for example 1% of requests may be slow).
3. Burn rate = the current error rate / the allowed rate. A rate of 1 uses exactly the budget over the window.
4. **Multi-window alerts:** page on a fast, high burn (like 14× over 1 hour), and open a ticket on a slow burn (like 2× over 3 days).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** The agent includes quality SLOs (recall, freshness), not just latency and availability, and pauses risky changes when the budget is low.
- **Rules:** Every retrieval system has SLOs for latency, availability, freshness (#182) and recall (#156).
- **Guardrails:** When the error budget is exhausted, freeze non-critical changes (index swaps, migrations) until it recovers.

### 181. Distributed tracing (OpenTelemetry)

**Definition:** Following one request across all services, with timing for each step, linked by a shared trace ID.

**How it works:**
1. The entry point creates a trace ID and passes it along in request headers (W3C Trace Context standard).
2. Each service creates spans: named, timed operations with attributes (such as index name, ef, k, candidate counts, filter selectivity).
3. Spans form a tree showing parent/child relationships and parallel work.
4. They're exported via OpenTelemetry (a CNCF project) to a tracing backend.
5. Sampling keeps the cost down: head sampling (decided at the start) or tail sampling (keep slow and failed traces).

**Agent use:**
- **Role:** Observer.
- **How:** Shows exactly where a slow or bad retrieval spent its time and what it did: which index, which parameters, how many candidates each stage kept.
- **Rules:** Agent tool calls (search, embed, rerank) propagate the trace context, so agent steps and backend spans appear in one trace.
- **Guardrails:** Never put raw query text, document content or secrets in span attributes unless privacy rules allow it (VG2). Use IDs and hashes.

### 182. Freshness lag (ingest-to-searchable)

**Definition:** The time between a change at the source and that change being reflected in search results.

**How it works:**
1. Each change carries its source timestamp (#128).
2. When it becomes searchable (after embedding, writing and refresh), record the visibility time.
3. Freshness lag = visibility time − source time. Track its percentiles.
4. Also measure end-to-end with probes (#195): write a marker document, then time until it's searchable.
5. Deletes are measured separately: the time until a deleted item stops appearing.

**Agent use:**
- **Role:** Observer.
- **How:** Tells the agent whether search results can be trusted for recent changes, and catches pipeline stalls.
- **Rules:** Set separate SLOs for update freshness and delete freshness. Deletes usually need a tighter one.
- **Guardrails:** Alert when lag exceeds the SLO. A stalled pipeline otherwise silently serves stale data.

### 183. Graph index health

**Definition:** Monitoring the structural quality of graph-based ANN indexes.

**How it works:**
1. **Reachability:** the share of nodes reachable from the entry point(s) (#74).
2. **Degree distribution:** the average and minimum number of outgoing and incoming edges. Nodes with no incoming edges can't be found.
3. **Deleted-node share** among the nodes traversed during searches.
4. **Search effort:** the average number of distance computations or hops per query. Rising effort at constant recall means degradation.

**Agent use:**
- **Role:** Observer.
- **How:** Catches silent graph degradation after many updates and deletes, and triggers repair or rebuild (#117, #146).
- **Rules:** Run the health checks after bulk deletes and on a schedule.
- **Guardrails:** Unreachable nodes are a silent recall loss. Alert on any meaningful number of them.

### 184. Tombstone ratio

**Definition:** The share of stored vectors that are marked deleted but not yet physically removed.

**How it works:**
1. Per segment: deleted count / total count.
2. Track it overall and per segment.
3. A high ratio wastes memory and search work, and in graphs, damages navigation.
4. It drops after compaction (#115) or repair (#117).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** Drives compaction and rebuild scheduling (#146).
- **Rules:** Set thresholds (for example 10–20%) that trigger maintenance.
- **Guardrails:** Tombstoned data still physically exists until compaction. This matters for deletion promises (#150).

### 185. Cache hit ratio and memory pressure

**Definition:** Monitoring how often data is found in memory, and whether memory is running out.

**How it works:**
1. Track the hit ratio of each cache: embedding cache (#50), result cache (#104), the OS page cache for memory-mapped indexes (#107).
2. Track memory use, page faults (major faults mean disk reads), and evictions.
3. A falling hit ratio combined with rising major faults means the working set no longer fits in RAM.
4. Correlate with latency (#178).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** Explains latency spikes that are caused by memory, not algorithms, and guides capacity changes (more RAM, more quantization, more shards).
- **Rules:** Size memory from the measured working set, with headroom.
- **Guardrails:** Alert on sustained major page faults on index hosts.

### 186. Capacity planning with Little's Law

**Definition:** Relating throughput, latency and concurrency to size the system: L = λ × W.

**How it works:**
1. L = average number of requests in the system (concurrency).
2. λ = arrival rate (requests per second).
3. W = average time each request spends in the system (latency).
4. Example: 500 QPS × 0.1 s = 50 concurrent requests on average. Size workers, connections and memory for that, plus headroom for peaks.
5. When latency rises at the same traffic level, concurrency rises too, which can cascade into overload.

**Agent use:**
- **Role:** Operator.
- **How:** The agent sizes thread pools, connection pools and replicas from measured traffic and latency, instead of guessing.
- **Rules:** Plan for peak traffic, not the average, with headroom (for example 30–50%).
- **Guardrails:** Combine with admission control (#109), so overload degrades gracefully instead of collapsing.

### 187. Consumer lag (stream backlog)

**Definition:** How far behind the ingestion consumers are relative to the newest events in the stream.

**How it works:**
1. For each stream partition, lag = the newest offset − the consumer's committed offset.
2. Convert to time lag using event timestamps.
3. Track lag per partition. One stuck partition can hide behind healthy averages.
4. Rising lag means consumers are too slow, stuck on a bad message, or crashed.

**Agent use:**
- **Role:** Observer.
- **How:** The leading indicator for freshness problems (#182). The agent detects a stuck pipeline before users notice stale results.
- **Rules:** Alert on lag per partition, including the deletes stream.
- **Guardrails:** A message that repeatedly fails must go to a dead-letter queue after N retries, never block the partition forever.

### 188. Cardinality-safe metric labels

**Definition:** Designing metric labels (dimensions) so the number of distinct time series stays bounded.

**How it works:**
1. Each unique combination of label values creates a separate time series.
2. Labels with unbounded values (user ID, query text, document ID) explode the series count and can take down the metrics system.
3. Use bounded labels: index name, stage, status code, tenant tier, query-type bucket.
4. Put high-cardinality details in traces (#181) or logs (#192), not metrics.

**Agent use:**
- **Role:** Observer.
- **How:** When the agent adds instrumentation, it chooses labels carefully, so observability stays affordable and reliable.
- **Rules:** No user IDs, query text, document IDs or raw tenant IDs (for large tenant counts) as metric labels.
- **Guardrails:** Monitor the series count per metric, and alert on sudden growth.

### 189. Anomaly detection on metrics

**Definition:** Automatically detecting unusual metric behavior, with smoothing and seasonality.

**How it works:**
1. **EWMA:** an exponentially weighted moving average and variance. Flag values more than k standard deviations from the average.
2. **Seasonal baselines:** compare with the same hour last week, or decompose into trend, seasonality and residual (as STL does).
3. **Change-point detection (CUSUM):** accumulates small deviations to detect lasting shifts.
4. Combine with fixed SLO thresholds (#180).

**Agent use:**
- **Role:** Observer.
- **How:** Catches subtle problems that thresholds miss: a slowly falling top-1 score (#171), a creeping OOD rate (#177), or recall drifting down.
- **Rules:** Use anomaly alerts as tickets or warnings; page only on SLO-based alerts.
- **Guardrails:** Suppress alerts during known events (deployments, migrations) and record them, so they aren't learned as normal.

### 190. Quantile sketches (t-digest, DDSketch)

**Definition:** Compact data structures that estimate percentiles from huge streams, and can be merged across machines.

**How it works:**
1. **t-digest:** keeps clusters of values (centroids with counts), with smaller clusters near the extremes, so tail percentiles are accurate.
2. **DDSketch:** logarithmic buckets that guarantee a relative error (for example ±1%) on any percentile.
3. Each machine keeps its own sketch.
4. Sketches merge correctly, so you get accurate global percentiles, unlike averaging per-machine percentiles.

**Agent use:**
- **Role:** Observer.
- **How:** Gives the agent accurate latency and score percentiles across shards and replicas.
- **Rules:** Merge sketches or histograms. Never average percentiles.
- **Guardrails:** None specific.

## D4. Debugging, audit and feedback

### 191. Query explain (per-stage breakdown)

**Definition:** A per-query report of what each retrieval stage did: candidates in, candidates out, timing and decisions.

**How it works:**
1. Each stage records: input count, output count, time, and key parameters.
2. Stages: routing (#98), filter planning (#83), ANN search (ef or nprobe), re-scoring, fusion, reranking, final cut.
3. For debugging a specific result, record its rank and score at each stage.
4. Return this report on request (a debug flag) or attach it to traces (#181).

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** When a known relevant document is missing, the agent can see where it was lost: never retrieved, filtered out, or dropped by the reranker. Then it fixes that stage.
- **Rules:** Explain mode is available for every query path, including filtered and hybrid.
- **Guardrails:** Explain output contains document IDs and scores. It's subject to the same access controls as the results (VG1).

### 192. Retrieval trace logging with sampling

**Definition:** Recording, for a sample of requests, the full context of a retrieval: query, parameters, results and versions.

**How it works:**
1. For sampled requests (plus all errors and slow ones), log: query ID, query hash or redacted text, model and index versions, filters, parameters, result IDs with scores, and the final answer ID if it was used for generation.
2. Link them to traces (#181).
3. Store with retention limits and access controls.
4. These logs enable replay, ground-truth comparison (#157) and failure analysis (#194).

**Agent use:**
- **Role:** Observer.
- **How:** Lets the agent reproduce any past retrieval exactly: same query, same snapshot, same parameters.
- **Rules:** Log versions (model, index, snapshot) on every record (V1).
- **Guardrails:** Apply privacy rules (VG2): redact or hash personal data, limit retention, and restrict access.

### 193. Embedding-space visualization

**Definition:** Projecting embeddings to 2D or 3D to visually inspect structure, clusters and problems.

**How it works:**
1. Sample vectors from the corpus, and possibly also queries.
2. Project them with UMAP or t-SNE (#27, #28), or PCA for a faster linear view.
3. Color by metadata: source, tenant, date, label, retrieval success or failure.
4. Look for patterns: duplicate clusters, failing queries landing in empty areas, separated languages, outliers.

**Agent use:**
- **Role:** Observer.
- **How:** Quick insight during investigations: where do failing queries fall relative to the corpus?
- **Rules:** Use it to form hypotheses, then confirm with metrics.
- **Guardrails:** Projections distort distances. Never make decisions from plot distances alone.

### 194. Failure clustering

**Definition:** Grouping failed retrievals by similarity to find shared root causes.

**How it works:**
1. Collect failures: no hit (#161), negative feedback (#165), low faithfulness (#167), OOD queries (#177).
2. Embed the failed queries and cluster them (#39).
3. Inspect each cluster: is it a missing topic, a bad chunk type, a terminology mismatch, or a filtering bug?
4. Prioritize the clusters by size and impact.
5. Fix the cause, then add cluster examples to the golden set (#164).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** Turns many individual complaints into a few actionable causes, such as "acronym queries fail" leading to a query-expansion fix.
- **Rules:** Each fix is validated on the cluster's queries and on the full golden set.
- **Guardrails:** Fixes for one cluster can regress others. Always run the full regression set.

### 195. Canary queries and synthetic probes

**Definition:** Fixed test queries and test documents that run continuously to check the system end to end.

**How it works:**
1. **Canary queries:** fixed queries with known expected results, run every few minutes.
2. **Write probes:** insert a unique marker document, then measure the time until it's searchable (#182), then delete it and measure the time until it disappears.
3. **Isolation probes:** query as tenant A for a marker that exists only for tenant B. Expect zero results.
4. Alert on any failure.

**Agent use:**
- **Role:** Observer.
- **How:** Detects broken deployments, stalled pipelines and isolation failures within minutes, even with no user traffic.
- **Rules:** Probes cover search, write freshness, delete freshness and tenant isolation.
- **Guardrails:** Probe documents are clearly marked and excluded from real users' results and from analytics.

### 196. Shadow traffic comparison

**Definition:** Sending a copy of real queries to a new configuration and comparing its results with production, without affecting users.

**How it works:**
1. Mirror a sample of production queries to the candidate system (a new model, index or parameters).
2. Users only see production results.
3. Compare the result overlap (Jaccard, rank correlation), score distributions, latency and errors.
4. Inspect queries where the results differ a lot, using judges (#163) or reviewers.
5. Promote the candidate only when the comparisons pass.

**Agent use:**
- **Role:** Observer and Operator.
- **How:** The agent validates migrations (#121, #149) on real traffic before the alias swap (#123).
- **Rules:** The shadow system gets the same filters and permissions as production (VG1).
- **Guardrails:** Shadow traffic must have no side effects, and must not count toward user analytics or billing.

### 197. Data lineage

**Definition:** Being able to trace any vector back to its source data and the exact transformations that produced it.

**How it works:**
1. Each vector stores (V1): source system and ID, source version, content hash, chunk position, chunker version, model and version, preprocessing version, quantization and codebook version, and ingestion time.
2. Each pipeline run records its configuration and code version.
3. Given a result, you can answer which source, which version, and how it was processed.
4. Given a source, you can list every vector derived from it (needed for deletion, #150).

**Agent use:**
- **Role:** Observer and Indexer.
- **How:** Enables precise deletions, targeted re-processing ("re-embed everything from chunker v3") and trustworthy citations in answers.
- **Rules:** Writes without complete lineage are rejected.
- **Guardrails:** Lineage metadata may itself be sensitive (paths, titles). Apply access controls (VG1).

### 198. Reconciliation checks

**Definition:** Regularly comparing what should be in the index with what is actually there.

**How it works:**
1. Count the source items that should be indexed, per collection and tenant.
2. Count the indexed items, per collection and tenant, and compare.
3. For mismatches, compare ID sets (or Merkle trees, #127) to find the missing and extra items.
4. Check the content hashes of a sample, to find stale vectors.
5. Report and repair: re-ingest missing items, delete extra ones.

**Agent use:**
- **Role:** Observer.
- **How:** Used before every alias swap (#123), after migrations (#121), after rebalancing (#139), and on a schedule.
- **Rules:** A swap or a source-data deletion requires a passed reconciliation.
- **Guardrails:** Large mismatches stop automated operations and go to human review (VG5).

### 199. Cost per query and per item

**Definition:** Measuring what each retrieval and each indexed item costs, across all components.

**How it works:**
1. Attribute resource use to each request: embedding calls (tokens), CPU and GPU time, memory share, disk reads, reranker calls, LLM judge calls.
2. Convert it to money with unit prices.
3. Track it per query type, per tenant and per pipeline stage.
4. For indexing: cost per embedded item, plus storage cost per vector per month.

**Agent use:**
- **Role:** Observer and Operator.
- **How:** Shows where cost goes (often reranking or LLM calls) and supports trade-offs: lower ef, smaller rerank sets, more caching, more quantization.
- **Rules:** Every cost optimization comes with a quality check (V5).
- **Guardrails:** Set budgets per agent and tenant, with alerts. Runaway agent loops are a real cost risk (#109).

### 200. Feedback loop into improvement

**Definition:** Systematically turning observed failures into fixes, test cases and training data.

**How it works:**
1. **Detect:** monitors and metrics (#156–190) and failure clustering (#194).
2. **Diagnose:** explain (#191), traces (#181), lineage (#197).
3. **Fix the right layer:** content (missing documents), chunking, embeddings (fine-tuning with hard negatives, #8), index parameters (#110), fusion or reranking, or generation.
4. **Lock it in:** add the failure cases to the golden set (#164).
5. **Validate and ship:** shadow test (#196), alias swap (#123), monitor.

**Agent use:**
- **Role:** Operator (the overall process).
- **How:** The agent runs this as a repeating cycle, so the retrieval system improves measurably over time instead of drifting.
- **Rules:** Every change is linked to the failure it fixes and the metrics that prove it.
- **Guardrails:** Changes to models, deletion policies or whole-corpus operations still need human approval (VG5).

## How the 200 entries fit together

1. **Transform (Transformer):** chunk (#11–13), embed with the right prefix and pooling (#1–6), normalize (#15–18), cache by content hash (#50), and validate vectors before writing (#172).
2. **Index (Indexer):** choose the index by scale and dimension (#57–79), compress if needed (#33–46), and declare filter fields (#154).
3. **Search (Retriever):** hybrid retrieval (#85–88), filters inside the search (#80–84), re-scoring (#93), reranking (#94–96), MMR (#89), with bounded k and access filters on every query.
4. **Update:** upserts with stable IDs (#111), CDC or an outbox (#125–126), idempotency (#129), deletes first (#132), tombstones and compaction (#115–117), migrations with dual-write and alias swaps (#121–123).
5. **Observe (Observer):** recall against ground truth (#156–157), golden-set regression (#164), drift (#168–177), SLOs on latency, freshness and recall (#178–182), probes (#195), reconciliation (#198), and the feedback loop (#200).
