# Part 3: Vector update (#111–155)

Same format and the same contract (roles; rules V1–V8; guardrails VG1–VG6).

## C1. Write path and index maintenance

### 111. Upsert by stable ID

**Definition:** Insert-or-replace keyed by a deterministic ID, so writing the same item twice updates it instead of duplicating it.

**How it works:**
1. Derive the ID deterministically: hash(source ID + chunk ID + model version), never a random UUID per write.
2. On write, look the ID up. If it's absent, insert the vector and metadata.
3. If it's present, mark the old version deleted (tombstone, #116) and insert the new one. Indexes rarely update vectors in place.
4. The new version becomes visible at the next refresh or commit.
5. A write with identical content (same content hash) can be skipped entirely.

**Agent use:**
- **Role:** Indexer.
- **How:** Every write the agent makes is an upsert with a deterministic ID, so retries, replays and re-runs never create duplicates (V4).
- **Rules:** The ID scheme is documented and versioned. Changing it means a full re-index.
- **Guardrails:** Before a bulk run, check the ID scheme on a sample. A non-deterministic ID (one including a timestamp) silently doubles the index on every re-run.

### 112. Write-ahead log (WAL)

**Definition:** Recording every write in an append-only durable log before applying it to the index.

**How it works:**
1. A write (upsert or delete) is appended to the log with a sequence number.
2. The log is flushed to disk (fsync), possibly batched across several writes (group commit).
3. Only then is the write acknowledged and applied to in-memory structures.
4. After a crash, replay the log from the last checkpoint to restore every acknowledged write.
5. Once a checkpoint (#138) covers a range of the log, that range can be truncated.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent treats a write as done only after it's durable, meaning acknowledged by the store, not merely sent.
- **Rules:** Track the store's last durable sequence number in the agent's own checkpoint (#130), so resumption starts at the right place.
- **Guardrails:** Disabling fsync for speed during bulk loads is acceptable only if the whole load can be safely re-run (idempotent, V4).

### 113. Fresh buffer (in-memory write segment)

**Definition:** A small, searchable in-memory area holding the newest vectors until they're merged into the main index.

**How it works:**
1. New vectors go into a small flat array, or a small graph index.
2. Queries search both the main index and the buffer, and merge the results.
3. A flat buffer is searched by brute force, which is exact and fast while it stays small.
4. When the buffer fills, it's frozen and flushed into a new segment (#114).
5. This gives near-instant visibility for new data without rebuilding big indexes.

**Agent use:**
- **Role:** Indexer and Retriever.
- **How:** The agent's freshly written vectors are searchable within seconds. Useful when the agent writes notes or findings and searches them in the same session.
- **Rules:** Know the store's visibility delay. Wait for, or explicitly request, a refresh before testing that new data is findable.
- **Guardrails:** A buffer that grows too large slows every query. Monitor its size.

### 114. Segment-based (LSM-style) vector storage

**Definition:** Storing vectors in many immutable segments, each with its own small index, merged over time.

**How it works:**
1. Flushed buffers become immutable segments, each with its own vector index (graph or IVF) and metadata.
2. Deletes and updates are recorded as tombstones in a per-segment deletion bitmap.
3. Queries search every segment and merge the results (#103).
4. Background merges combine small segments into larger ones (#115).
5. Immutability makes snapshots, caching and replication simple.

**Agent use:**
- **Role:** Indexer and Operator.
- **How:** The agent understands why query latency rises with many small segments, and why bulk loads should create few large segments (#148).
- **Rules:** Monitor the segment count, and trigger or wait for merges after bulk writes.
- **Guardrails:** Too many segments is a common hidden cause of slow search. Alert on segment count.

### 115. Segment merge and compaction

**Definition:** Combining segments into larger ones and dropping deleted vectors for good.

**How it works:**
1. A merge policy picks segments to merge: similar sizes (tiered), or segments with many deletions.
2. Read the live (non-deleted) vectors from the chosen segments.
3. Build a new index for the merged segment. Graph merges may re-insert vectors or join graphs.
4. Atomically swap the new segment in and the old ones out.
5. Delete old segment files once no query or snapshot uses them.

**Agent use:**
- **Role:** Operator.
- **How:** Compaction reclaims space and restores speed after heavy updates. It's also when deleted data is physically removed, which matters for deletion verification (#150).
- **Rules:** Schedule large merges off-peak, because they consume CPU and I/O.
- **Guardrails:** Deleted data isn't physically gone until compaction (and backup expiry). Account for that in deletion promises (V6).

### 116. Tombstone deletion (deletion bitmap)

**Definition:** Marking vectors as deleted with a bit, instead of removing them from the index immediately.

**How it works:**
1. Each segment keeps a bitmap with one bit per vector.
2. A delete sets the vector's bit.
3. Searches skip vectors whose bit is set, both during traversal and when collecting results.
4. The vectors and their graph edges stay in place until compaction or repair.
5. Deletion is instant and cheap; the storage is reclaimed later.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent's deletes take effect for search right away. It tracks the tombstone ratio (#184), since many tombstones hurt speed and, in graphs, recall.
- **Rules:** Verify a delete by searching for the deleted ID and its content right after (#150).
- **Guardrails:** If the tombstone ratio exceeds a threshold (for example 10–20%), schedule compaction or rebuild.

### 117. Deleting from HNSW (mark plus repair)

**Definition:** Handling deletions in a graph index without breaking navigation.

**How it works:**
1. **Soft delete:** mark the node deleted. Search still walks through it as a stepping stone but never returns it.
2. Over time, many deleted nodes waste work and can leave live nodes poorly connected.
3. **Repair:** for each live neighbor of a deleted node, reconnect it to candidates drawn from the deleted node's neighbors, using the normal neighbor-selection heuristic (#67).
4. Then remove the deleted node and its edges.
5. Run the repair in batches, or rebuild the graph once deletions are heavy.

**Agent use:**
- **Role:** Indexer and Observer.
- **How:** After large delete operations, the agent schedules a repair and checks connectivity (#74, #183).
- **Rules:** Measure recall after big deletions; don't assume it's unchanged.
- **Guardrails:** Replacing deleted node slots with new vectors without proper reconnection causes recall loss. Use the library's supported update path only.

### 118. In-place updates for disk graphs (FreshDiskANN style)

**Definition:** Supporting continuous inserts and deletes on a large disk-based graph through a small in-memory graph plus periodic batch merges.

**How it works:**
1. New inserts go into a small in-memory graph that's searched alongside the disk graph.
2. Deletes go into a delete list, filtered out during search.
3. A periodic merge streams through the disk graph: it removes deleted nodes and patches their neighbors' links (#117), and inserts the in-memory vectors into the disk graph.
4. The merged graph replaces the old one.
5. Both graphs keep serving queries during the merge.

**Agent use:**
- **Role:** Operator.
- **How:** Lets large disk indexes stay fresh without full rebuilds. The agent schedules merges by delete count and memory-graph size.
- **Rules:** Track the merge frequency and duration, and the recall after each merge.
- **Guardrails:** If the in-memory graph grows too big (merges falling behind), latency and memory rise. Alert on its size.

### 119. Incremental IVF assignment

**Definition:** Adding new vectors to an existing IVF index by assigning them to the nearest existing centroid.

**How it works:**
1. Compute the new vector's nearest centroid.
2. Append it (or its PQ code, computed with the existing codebook) to that list.
3. No retraining happens; the centroids stay fixed.
4. Lists slowly grow uneven as the data distribution shifts.

**Agent use:**
- **Role:** Indexer.
- **How:** Fast, simple updates for IVF indexes. The agent monitors list balance (#173) to know when retraining is due.
- **Rules:** New data must be encoded with the same centroids and codebooks as the index (V2).
- **Guardrails:** If new data is far from every centroid (a new topic area), recall for it drops. Track the distance to nearest centroid for new vectors (#168).

### 120. Centroid drift detection and retraining

**Definition:** Detecting when IVF centroids or PQ codebooks no longer fit the data, then retraining them.

**How it works:**
1. Monitor list size imbalance (#173), the average distance from vectors to their assigned centroid, and quantization error.
2. Compare those against the values at training time.
3. When thresholds are crossed, retrain the centroids and codebooks on a fresh representative sample.
4. Re-assign and re-encode all vectors into a new index (#147).
5. Swap it in by alias (#123) after validating recall.

**Agent use:**
- **Role:** Observer and Operator.
- **How:** The agent turns slow recall decay into an explicit, measured retraining decision.
- **Rules:** Retraining always produces a new index validated against the old one (V5). It never modifies the live index in place.
- **Guardrails:** Retraining on a biased sample (only recent data) can hurt older data. Sample across the whole corpus.

### 121. Re-embedding pipeline (model migration)

**Definition:** Re-computing every vector with a new embedding model and moving traffic to the new vectors.

**How it works:**
1. Create a new index (a new vector space) for the new model (V2).
2. Backfill: re-embed every source chunk from the source of truth (never from the old vectors), with checkpoints (#130).
3. Meanwhile, send new writes to both indexes (#122).
4. Evaluate: run golden-set comparisons (#164) and a shadow-traffic comparison (#196).
5. Switch the alias to the new index (#123). Keep the old one for rollback until the new one is proven.
6. Delete the old index after a retention period.

**Agent use:**
- **Role:** Operator.
- **How:** The agent plans and runs model upgrades as a controlled migration, never in place.
- **Rules:** Queries switch models at exactly the same moment the index switches (V3). Never let new-model queries hit old-model vectors.
- **Guardrails:** A full re-embed is expensive and needs human approval (VG5). Estimate the cost (tokens, GPU hours) and time up front.

### 122. Dual-write (shadow index)

**Definition:** Writing every change to both the current and the new index during a migration.

**How it works:**
1. The writer sends each upsert or delete to both indexes, each transformed for its own space.
2. If one write fails, record it for retry. The indexes must eventually converge.
3. Reads continue from the current index, or are mirrored to the new one for comparison (#196).
4. After the backfill finishes, both indexes hold the same set of IDs.
5. Reconciliation (#198) verifies that before the cutover.

**Agent use:**
- **Role:** Indexer.
- **How:** Keeps the new index from falling behind during a long backfill.
- **Rules:** Deletes must go to both indexes. A delete missing from the new index brings deleted content back after cutover (V6).
- **Guardrails:** Run ID-set reconciliation between the two indexes before switching.

### 123. Blue-green index swap (alias cutover)

**Definition:** Serving queries through an alias that can be switched atomically between two complete indexes.

**How it works:**
1. Queries target an alias ("docs-current") rather than a physical index.
2. Build and warm the new index (green) while the old one (blue) serves.
3. Validate green: recall, latency, counts, sample queries.
4. Atomically point the alias at green.
5. Keep blue intact for a rollback window, then delete it.

**Agent use:**
- **Role:** Operator.
- **How:** Every model change, parameter change or rebuild is deployed this way, with instant rollback (VG4).
- **Rules:** Warm the new index's caches before the switch (#107). Cold indexes cause latency spikes.
- **Guardrails:** Never delete the old index until the new one has served real traffic within its SLOs for the agreed window.

### 124. Idempotent ingestion with content-hash dedupe

**Definition:** Skipping the work of re-embedding and re-writing when the content hasn't changed.

**How it works:**
1. For each source chunk, compute a hash of its normalized content plus the transform configuration.
2. Compare it with the hash stored on the existing vector with the same ID.
3. If they match, skip the chunk.
4. If they differ, re-embed and upsert (#111).
5. Chunks that disappeared from the source are deleted (#144).

**Agent use:**
- **Role:** Transformer and Indexer.
- **How:** Re-running ingestion over a large corpus touches only what changed, which makes frequent syncs cheap and safe.
- **Rules:** The hash includes the transform configuration, so a model or chunking change correctly forces re-embedding (V1).
- **Guardrails:** Normalize before hashing (line endings, trailing whitespace), but not so aggressively that real changes are hidden.

## C2. Change capture and ingestion

### 125. Change data capture (CDC)

**Definition:** Streaming every insert, update and delete from a source database into the vector pipeline.

**How it works:**
1. Read the database's replication log (MySQL binlog, Postgres logical replication, MongoDB change streams).
2. Turn each change into an event with its key, operation, new values and log position.
3. Publish events to a durable stream (Kafka or similar), partitioned by key so the order per key is kept.
4. Vector pipeline consumers chunk, embed and upsert or delete accordingly.
5. Consumers record their stream offset after processing, so they can resume after a failure.

**Agent use:**
- **Role:** Indexer.
- **How:** Keeps the vector index in sync with the source of truth automatically, including deletes, with no batch jobs to miss changes.
- **Rules:** Process events in order per key. A late "update" must never overwrite a newer one (use versions, #140).
- **Guardrails:** Monitor consumer lag (#187). Deletes stuck in a lagging stream are a compliance risk (V6).

### 126. Transactional outbox

**Definition:** Writing a change event in the same database transaction as the business change, then publishing it reliably.

**How it works:**
1. In one transaction, write the business row and an event row in an outbox table.
2. The transaction guarantees both happen or neither does.
3. A relay process reads new outbox rows (by polling or CDC) and publishes them to the stream.
4. It marks rows as published, or deletes them, after acknowledgment.
5. Consumers must handle duplicates (the relay may republish after a crash), via idempotency (#129).

**Agent use:**
- **Role:** Operator (pipeline design).
- **How:** When an application writes data that must be embedded, the outbox guarantees no change is lost between the database and the vector index.
- **Rules:** Never "write to the database, then call the embedding pipeline" without an outbox. A crash between the two loses the update.
- **Guardrails:** Alert on outbox backlog age.

### 127. Merkle-tree sync (anti-entropy)

**Definition:** Comparing hash trees of the source and the index to find exactly what's out of sync.

**How it works:**
1. Build a hash tree over the source: leaves are item content hashes, and parents hash their children, grouped by ID range or path.
2. Build the same tree over what the index says it contains (IDs and content hashes from metadata).
3. Compare from the root down, descending only into subtrees whose hashes differ.
4. The differing leaves are the missing, extra or stale items.
5. Fix those items only.

**Agent use:**
- **Role:** Observer and Indexer.
- **How:** A periodic check that catches anything CDC or events missed, in time proportional to the differences, not the corpus size.
- **Rules:** Run it on a schedule and after incidents.
- **Guardrails:** Extra items in the index (present in the index, absent from the source) are deleted. Those are often items that should have been removed (V6).

### 128. Watermarks and freshness tracking

**Definition:** Tracking how far the pipeline has processed, in event time, so the delay from source change to searchability is known.

**How it works:**
1. Each event carries its source change time.
2. Each pipeline stage reports a watermark: "all events up to time T have been processed".
3. The index's freshness = now − the oldest watermark in the chain.
4. Late or out-of-order events are handled according to policy: processed late, or flagged.

**Agent use:**
- **Role:** Observer and Retriever.
- **How:** The agent can tell users how fresh the index is ("data as of 3 minutes ago") and knows when not to trust it for very recent changes.
- **Rules:** Expose the index's freshness alongside search results for time-sensitive use cases.
- **Guardrails:** Alert when freshness exceeds the SLO (#182).

### 129. Exactly-once effects via idempotency keys

**Definition:** Making sure each change affects the index exactly once, even though messages may be delivered more than once.

**How it works:**
1. Streams usually guarantee at-least-once delivery, so duplicates happen.
2. Each change carries a unique key and version: (item ID, source version).
3. The writer applies a change only if its version is newer than the stored one. Otherwise it's skipped.
4. Combined with deterministic upsert IDs (#111), duplicates have no effect.
5. Some systems also commit stream offsets and writes in one transaction.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent never relies on "the message only arrives once". Every write path is idempotent.
- **Rules:** Store the source version on every vector (V1). Compare versions before writing.
- **Guardrails:** Never use wall-clock time from different machines as the version. Clocks disagree, so use source sequence numbers.

### 130. Backfill with checkpoints

**Definition:** Processing an entire historical corpus in resumable chunks.

**How it works:**
1. Split the corpus into ordered units (ID ranges, partitions, files).
2. Process each unit: read, chunk, embed, upsert.
3. After each unit, durably record that it's done, with counts and the last ID.
4. On a crash or restart, continue from the last checkpoint.
5. Meanwhile, live changes flow through CDC or dual-write, so the backfill and live updates must not overwrite each other incorrectly (versions, #129).

**Agent use:**
- **Role:** Operator and Indexer.
- **How:** Re-embedding millions of chunks across hours or days survives restarts, rate limits and deployments.
- **Rules:** The backfill writes with the source version it read, so it never overwrites a newer live update.
- **Guardrails:** Throttle the backfill so it doesn't starve live traffic (#132). Report progress and an estimated completion time.

### 131. Batch versus streaming embedding (micro-batching)

**Definition:** Choosing between embedding changes immediately one by one, in small groups, or in large periodic batches.

**How it works:**
1. **Streaming:** each change is embedded on arrival. Lowest latency, worst hardware efficiency.
2. **Micro-batching:** collect changes for a short window (seconds) or until N items, then embed them together.
3. **Batch:** process large accumulated sets periodically. Most efficient, highest delay.
4. The choice depends on freshness requirements and cost.

**Agent use:**
- **Role:** Transformer.
- **How:** Micro-batching usually gives near-real-time freshness at a fraction of the per-item cost. The agent uses it for continuous sync.
- **Rules:** Set the batch window from the freshness SLO.
- **Guardrails:** One bad item must not fail its whole batch. Retry items individually and dead-letter persistent failures.

### 132. Backpressure and prioritized ingestion

**Definition:** Controlling ingestion speed and order so that important changes go first and the system isn't overloaded.

**How it works:**
1. Ingestion queues have limited capacity. When full, producers slow down or wait.
2. Separate queues (or priorities) for deletes, live updates and backfill.
3. **Deletes first:** they carry compliance risk. Then live updates (freshness). Then backfill.
4. Rate limits protect the embedding service and the index.

**Agent use:**
- **Role:** Operator and Indexer.
- **How:** During a large re-embed, user-visible updates and deletes still flow quickly.
- **Rules:** Deletes always have the highest priority.
- **Guardrails:** Monitor queue depth per priority level. Persistent growth means capacity is too low.

## C3. Consistency, replication and recovery

### 133. MVCC snapshots

**Definition:** Each query reads a consistent snapshot of the index while writes continue.

**How it works:**
1. Every commit creates a new version: a set of segments plus deletion bitmaps.
2. A query pins the version current when it starts.
3. Writes create new versions without changing the pinned one.
4. Old versions are cleaned up when no query uses them.

**Agent use:**
- **Role:** Retriever.
- **How:** Multi-step agent workflows (search, then fetch details, then search again) can pin one snapshot to see consistent data.
- **Rules:** Record the snapshot or version used in retrieval traces (#192).
- **Guardrails:** Long-held snapshots keep old data alive and block cleanup. Set a maximum pin time.

### 134. Consistency levels (read-your-writes)

**Definition:** Choosing how up to date a read must be relative to recent writes.

**How it works:**
1. **Eventual:** reads may miss recent writes for a while. Fastest.
2. **Read-your-writes / session:** a client always sees its own writes. The client passes its last write token, and the server waits until that write is visible.
3. **Bounded staleness:** reads are at most T seconds behind.
4. **Strong:** reads see all acknowledged writes. Slowest.

**Agent use:**
- **Role:** Retriever and Indexer.
- **How:** When the agent writes something and immediately searches for it (for example to verify a write or a delete), it requests read-your-writes, not eventual consistency.
- **Rules:** Deletion verification (#150) always uses a consistency level that includes the delete.
- **Guardrails:** "Not found right after a write" under eventual consistency isn't evidence of failure. Check the consistency level first.

### 135. Leader-follower replication

**Definition:** One node accepts writes and copies them to follower nodes, which serve reads.

**How it works:**
1. All writes go to the leader, which appends them to its log (#112).
2. The log is streamed to followers, which apply it in order.
3. Followers serve reads, possibly slightly behind (replication lag).
4. If the leader fails, a follower is promoted. Unreplicated writes may be lost unless replication was synchronous.

**Agent use:**
- **Role:** Operator.
- **How:** The agent monitors replication lag and routes freshness-critical reads to the leader or to followers known to be caught up.
- **Rules:** Know whether writes are acknowledged before or after replication.
- **Guardrails:** Alert on replication lag. Large lag combined with failover means lost writes.

### 136. Raft consensus

**Definition:** An algorithm that keeps a replicated log consistent across nodes, tolerating failures, with a single elected leader.

**How it works:**
1. Nodes are followers, candidates or the leader. Time is divided into numbered terms.
2. If a follower hears nothing from a leader for a timeout, it becomes a candidate and asks for votes. A majority makes it leader for that term.
3. The leader appends client writes to its log and replicates them.
4. An entry is committed once a majority has stored it. Committed entries are never lost.
5. Followers with conflicting log entries are overwritten by the leader's log.

**Agent use:**
- **Role:** Operator.
- **How:** Many distributed vector databases use Raft for metadata and log replication. The agent knows that writes need a majority, so losing a majority stops writes.
- **Rules:** Run an odd number of nodes (3 or 5) across failure domains.
- **Guardrails:** During leader elections, writes pause briefly. Retry with backoff rather than failing the job.

### 137. Quorum reads and writes

**Definition:** Requiring a minimum number of replicas to acknowledge a write (W) and to answer a read (R).

**How it works:**
1. With N replicas, a write succeeds when W replicas confirm it, and a read queries R replicas.
2. If R + W > N, every read overlaps at least one replica holding the latest write.
3. The read returns the version with the highest version number among the answers.
4. Background repair updates stale replicas.

**Agent use:**
- **Role:** Operator.
- **How:** The agent chooses R and W per use case: higher W for durability of important writes like deletes, lower R for fast reads.
- **Rules:** Deletes use a write quorum that guarantees they're visible to all later quorum reads (V6).
- **Guardrails:** Sloppy quorums (writing to substitute nodes during failures) weaken guarantees. Know whether your store uses them.

### 138. Snapshot plus log replay recovery

**Definition:** Restoring an index from a periodic full snapshot plus the log of changes since.

**How it works:**
1. Periodically write a consistent snapshot (segments, metadata, the index state) to durable storage, with its log sequence number.
2. Keep the WAL from that point on.
3. **Recovery:** load the latest snapshot, then replay the log entries after its sequence number.
4. Test restores regularly. A backup that has never been restored is unproven.

**Agent use:**
- **Role:** Operator.
- **How:** The agent includes restore tests in operations, and knows the recovery time (snapshot size plus log length).
- **Rules:** Deletions after a snapshot must replay correctly. Test restore on data with recent deletes.
- **Guardrails:** Snapshots and backups contain deleted data until they expire. Include them in deletion policies (#150).

### 139. Consistent-hashing rebalancing

**Definition:** Redistributing vectors when shards are added or removed, moving as little data as possible.

**How it works:**
1. Shards and keys are placed on a hash ring. Each key belongs to the next shard clockwise.
2. Adding a shard moves only the keys between it and its predecessor.
3. Virtual nodes (many ring positions per shard) spread the load evenly.
4. Data moves in the background: copy, verify, switch ownership, delete from the old shard.
5. During the move, reads must check both shards or the routing table.

**Agent use:**
- **Role:** Operator.
- **How:** The agent plans scale-out with predictable data movement and no downtime.
- **Rules:** Verify the counts after moving (#198) before deleting the source copies.
- **Guardrails:** Throttle rebalancing so it doesn't hurt query latency.

### 140. Version vectors and conflict detection

**Definition:** Per-replica counters attached to each item, which reveal whether two versions are ordered or truly concurrent.

**How it works:**
1. Each item carries a vector of counters, one per writer or replica.
2. A writer increments its own counter when it changes the item.
3. Comparing two versions: if every counter of A is ≤ B's, then A happened before B. If neither dominates, they're concurrent, which is a conflict.
4. Conflicts are resolved by a rule (last-writer-wins with care, a merge, or a source-of-truth re-read).

**Agent use:**
- **Role:** Indexer (multi-region or multi-writer setups).
- **How:** Prevents an older embedding from overwriting a newer one when updates arrive through different paths.
- **Rules:** For derived data like vectors, resolve conflicts by re-reading the source of truth and re-embedding.
- **Guardrails:** Pure wall-clock last-writer-wins across regions can silently lose updates. Avoid it for critical data.

### 141. Schema and metadata versioning

**Definition:** Versioning the metadata fields stored with vectors (filters, lineage), so changes don't break queries or writers.

**How it works:**
1. Each record or collection carries a schema version.
2. Changes are additive first: add a new field, write both old and new, migrate readers, then remove the old field (expand and contract).
3. Filter indexes are built for new fields before queries use them.
4. Readers handle missing fields on older records.

**Agent use:**
- **Role:** Indexer and Operator.
- **How:** Adding a new filter field (for example "department") is planned as a migration with a backfill, not a sudden change.
- **Rules:** Lineage fields (V1) are mandatory in every schema version.
- **Guardrails:** A query filtering on a field that older records lack silently excludes them. Backfill before relying on the field.

### 142. Multi-tenant isolation

**Definition:** Ensuring each tenant's vectors are only searchable and modifiable by that tenant.

**How it works:**
1. **Physical:** a separate index or partition per tenant (#84).
2. **Logical:** a shared index with a mandatory tenant filter applied inside the search (#80, #82).
3. The tenant ID comes from the authenticated request, never from user input.
4. Per-tenant quotas protect the others (#109).
5. Deleting a tenant removes its partition, or all its records plus their caches and backups.

**Agent use:**
- **Role:** Retriever and Indexer.
- **How:** Every agent query and write carries a tenant identity derived from authentication. The agent can't query across tenants.
- **Rules:** Tenant filters are enforced server-side, inside the search (VG1).
- **Guardrails:** Test isolation regularly: canary queries (#195) from tenant A must never return tenant B's data.

## C4. Lifecycle management

### 143. TTL (time-to-live) expiry

**Definition:** Automatically removing vectors after a set time.

**How it works:**
1. Each record stores an expiry time.
2. Searches exclude expired records immediately, through a time filter.
3. A background job deletes them physically (tombstones, then compaction).
4. TTL is often used for session data, temporary agent memory and logs.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent sets TTLs on temporary data (scratch notes, short-lived caches), so they don't accumulate and resurface later.
- **Rules:** The default TTL for agent working memory is explicit and documented.
- **Guardrails:** Check that expired data is excluded from search before the physical deletion runs.

### 144. Orphan garbage collection

**Definition:** Finding and removing vectors whose source no longer exists.

**How it works:**
1. List the source IDs from the source of truth.
2. List the source IDs referenced by the index's vectors (from lineage metadata, V1).
3. Vectors whose source ID isn't in the source list are orphans.
4. Delete them in batches, after a safety check (#198).
5. Run it periodically and after migrations.

**Agent use:**
- **Role:** Indexer and Observer.
- **How:** Catches data that should have been deleted but wasn't (missed delete events, failed jobs).
- **Rules:** Orphan deletion needs a complete source listing. A partial listing would delete valid data.
- **Guardrails:** If more than a small fraction of the index would be deleted, stop and require human review (VG5).

### 145. Near-duplicate deduplication

**Definition:** Detecting and merging vectors whose content is nearly identical.

**How it works:**
1. Exact duplicates: same content hash.
2. Near duplicates: SimHash or MinHash fingerprints (#31) to find candidates, then cosine similarity above a high threshold (#90) to confirm.
3. Choose a canonical copy (newest, most authoritative source) and keep links to the others.
4. Either drop the duplicates from the index or collapse them at query time.

**Agent use:**
- **Role:** Transformer and Indexer.
- **How:** Duplicates waste storage and crowd retrieval results with copies. The agent dedupes at ingestion, or collapses at query time with MMR (#89).
- **Rules:** Keep lineage for all copies, so deleting one source doesn't remove content that another source still provides.
- **Guardrails:** Confirm near-duplicates with text comparison before deleting. Similar vectors can belong to meaningfully different documents (versions, other languages).

### 146. Rebuild scheduling

**Definition:** Deciding when to rebuild an index fully, instead of continuing incremental updates.

**How it works:**
1. Track the signals: tombstone ratio (#184), recall decay (#156), list imbalance (#173), segment count (#114), unreachable nodes (#183).
2. Set thresholds for each.
3. When thresholds are crossed, schedule a rebuild off-peak.
4. Build the new index alongside the old one (#147), validate, and swap (#123).

**Agent use:**
- **Role:** Observer and Operator.
- **How:** The agent turns index decay into planned maintenance instead of noticing it through user complaints.
- **Rules:** Rebuild decisions record the signal values that triggered them.
- **Guardrails:** Never rebuild in place on the serving index.

### 147. Online index build

**Definition:** Building a new index while the old one keeps serving, then catching up on changes made during the build.

**How it works:**
1. Record the current position of the change log (or snapshot version).
2. Build the new index from a consistent snapshot at that position.
3. When the build finishes, replay the changes made since that position (#138).
4. Repeat the catch-up until the lag is small.
5. Swap atomically (#123).

**Agent use:**
- **Role:** Operator.
- **How:** The way to do rebuilds, retraining (#120) and requantization (#149) without downtime.
- **Rules:** Verify ID counts and a sample of contents before the swap (#198).
- **Guardrails:** The catch-up must include deletes; missing them re-exposes deleted data (V6).

### 148. Bulk loading

**Definition:** Building an index from a large dataset in one efficient operation, instead of inserting vectors one by one.

**How it works:**
1. Load all vectors, ideally sorted or grouped (for example by cluster).
2. Train the quantizers and centroids once on a sample.
3. Build the index in parallel: build partitions or subgraphs separately, then merge.
4. Write large segments directly, instead of many small flushed segments.
5. Run checks: counts, recall on a sample.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent uses the store's bulk-import path for initial loads and full rebuilds. It's much faster than upserting millions of items through the online path.
- **Rules:** Bulk loads target a new index, not the serving one.
- **Guardrails:** Validate counts and recall before swapping (V5).

### 149. Requantization migration

**Definition:** Changing an index's compression (for example float32 → int8 → binary with re-scoring) as a controlled migration.

**How it works:**
1. Keep the full-precision vectors as the source (#93).
2. Train the new quantization parameters (ranges, codebooks).
3. Build the new index from the full vectors (#147).
4. Measure recall and latency against the current index (V5).
5. Swap by alias (#123) if the new index meets targets.

**Agent use:**
- **Role:** Operator.
- **How:** The agent can cut memory cost with measured risk, and roll back if quality drops.
- **Rules:** Never requantize from already-quantized vectors. Always start from full precision.
- **Guardrails:** Check recall per segment (tenants, topics), since compression hurts some data more than others.

### 150. Deletion verification ("right to be forgotten")

**Definition:** Proving that deleted content no longer appears anywhere in retrieval, and is removed from storage within the promised time.

**How it works:**
1. Delete by source ID: find all vectors with that lineage (V1), including chunks, duplicates and both indexes during migrations.
2. Delete them, with read-your-writes consistency (#134).
3. Verify: search by ID, by exact content, and by its embedding (nearest-neighbor search for the deleted text) to confirm nothing is returned.
4. Purge caches: embedding cache (#50), result and semantic caches (#104, #105).
5. Physical removal: compaction (#115) and backup expiry (#138), within the policy's deadline.
6. Log the deletion with its verification evidence.

**Agent use:**
- **Role:** Indexer and Observer.
- **How:** The agent runs deletion as a checklist with evidence, not a single API call.
- **Rules:** V6: every deletion request produces a verification record.
- **Guardrails:** Deletion policies and their deadlines are set by humans (VG5). The agent reports where data still physically exists (backups) and until when.

## C5. Transformation during updates

### 151. Backward-compatible embeddings (BCT)

**Definition:** Training a new embedding model so its vectors remain comparable to the old model's vectors.

**How it works:**
1. Train the new model with an extra loss term that keeps its embeddings compatible with the old model's space. For example, new query vectors should still rank old document vectors correctly.
2. New queries can then search old document vectors with acceptable quality.
3. This allows the model to be upgraded first and documents re-embedded gradually.
4. Quality is best after the full re-embed, but service never breaks during it.

**Agent use:**
- **Role:** Operator.
- **How:** When re-embedding everything at once is too costly, compatible training allows gradual migration.
- **Rules:** Treat the compatibility as an assumption to measure: check mixed-space recall on golden queries (#164).
- **Guardrails:** Without compatibility training, V2 applies strictly: never mix model versions.

### 152. Lazy (on-read) re-embedding

**Definition:** Re-embedding items gradually, prioritizing items as they're read or updated, instead of all at once.

**How it works:**
1. Mark each vector with its model version.
2. When an item is updated, or retrieved frequently, re-embed it with the new model.
3. A background job re-embeds the rest, ordered by importance (traffic, recency).
4. Until migration is complete, queries must target a consistent space: either a compatible model (#151) or a dual index (#122).

**Agent use:**
- **Role:** Operator and Transformer.
- **How:** Spreads re-embedding cost over time and does the most important items first.
- **Rules:** Track the migration percentage per collection. Complete the migration within a planned period.
- **Guardrails:** Never compare vectors from different spaces in one ranking unless they're compatible by design (#151).

### 153. Codebook retraining

**Definition:** Re-learning PQ or IVF quantization parameters when the data has shifted, then re-encoding vectors.

**How it works:**
1. Detect rising quantization error or recall decay (#120).
2. Sample current data representatively.
3. Train new codebooks (and rotation, for OPQ, #36).
4. Re-encode every vector from full precision into a new index.
5. Validate and swap (#123).

**Agent use:**
- **Role:** Operator.
- **How:** Restores compressed-index quality after the corpus changes significantly (new topics, new languages).
- **Rules:** Codebook versions are part of index lineage. Never mix codes from two codebook versions.
- **Guardrails:** Same validation discipline as any new index (V5).

### 154. Metadata index maintenance

**Definition:** Keeping the indexes on filterable metadata fields (B-trees, bitmaps, inverted lists) in sync with the vectors.

**How it works:**
1. Each filterable field has an index: a B-tree for ranges (dates, numbers), bitmaps or inverted lists for categories (tenant, type).
2. Every upsert or delete updates both the vector index and the metadata indexes.
3. Statistics (value counts) are maintained for selectivity estimation (#83).
4. High-cardinality fields (unique IDs) use hash or B-tree indexes, not bitmaps.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent declares the filter fields up front, so filtered search is fast and correct.
- **Rules:** Index every field used in security filters (VG1).
- **Guardrails:** An unindexed filter field may force a slow scan or a post-filter fallback. Check the query plan.

### 155. Atomic vector and metadata commit

**Definition:** Making a vector and its metadata (including access fields) visible at the same moment.

**How it works:**
1. Write the vector, its metadata and the metadata index updates in one transaction or one segment commit.
2. Readers see either the complete new record or the complete old one.
3. If the store can't do this atomically, write the access metadata first and the vector last, so the vector is never visible without its filters.

**Agent use:**
- **Role:** Indexer.
- **How:** Prevents a window where a new vector is searchable but its tenant or ACL fields aren't set yet.
- **Rules:** Vectors without complete access metadata must be rejected at write time.
- **Guardrails:** Test the write path with concurrent searches to confirm no partially written records appear (VG1).
