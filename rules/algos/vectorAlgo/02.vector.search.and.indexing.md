# Part 2: Vector search (#51–110)

Same format and the same contract (roles; rules V1–V8; guardrails VG1–VG6).

## B1. Exact search and distance computation

### 51. Brute-force kNN with matrix multiplication (GEMM)

**Definition:** Exact nearest-neighbor search that scores the query against every vector, done as one matrix multiply.

**How it works:**
1. Stack all database vectors into an N × D matrix X.
2. Stack one or more queries into a Q × D matrix.
3. Multiply X by the transposed query matrix to get all dot products (Q × N scores) in one optimized BLAS or GPU call.
4. For L2 distance, use |x − q|² = |x|² + |q|² − 2x·q. The norms |x|² are precomputed once.
5. Select the top k per query (#53, #54).
6. Batching many queries uses the hardware far better than scoring one query at a time.

**Agent use:**
- **Role:** Retriever (small corpora) and Observer (ground truth).
- **How:** For collections up to a few hundred thousand vectors, the agent can skip building an index entirely, and results are exact. For larger indexes, the agent runs brute force on sampled queries to produce the ground truth that recall is measured against (#156, #157).
- **Rules:** Use brute force as the reference for every recall measurement (V5).
- **Guardrails:** Cap N and the batch size per call (VG3). Brute force over a large corpus on the request path can exhaust CPU or GPU.

### 52. SIMD distance kernels

**Definition:** Computing dot products and distances many components at a time using vector instructions.

**How it works:**
1. Load 8 (AVX2) or 16 (AVX-512) floats from the query and from the database vector.
2. Multiply and accumulate them in one fused instruction (FMA).
3. Repeat across the dimensions, keeping several accumulators to hide instruction latency.
4. Sum the lanes horizontally at the end.
5. Int8 and binary kernels use integer dot-product instructions or XOR + popcount (#34).

**Agent use:**
- **Role:** Indexer and Retriever (configuration).
- **How:** The agent checks that the deployment hardware supports the instructions the vector library was built for. A library falling back to scalar code can be many times slower.
- **Rules:** Choose dimensions that are multiples of 8 or 16 where possible, and check build flags.
- **Guardrails:** Benchmark on the actual production CPU type, not a developer laptop.

### 53. Top-k selection with a heap

**Definition:** Keeping the k best results while scanning many candidates.

**How it works:**
1. Keep a heap of size k ordered so the worst kept result is at the top.
2. For each candidate, if the heap holds fewer than k items, insert it.
3. Otherwise, compare with the worst kept result. If the candidate is better, replace it and fix the heap.
4. After the scan, sort the k items for output.
5. Cost is O(N log k), with memory O(k).

**Agent use:**
- **Role:** Retriever.
- **How:** Used everywhere: inside indexes, when merging shards (#103) and in rerankers. The agent keeps k small and asks for more only when needed (V7).
- **Rules:** Break ties deterministically (by ID), so results are reproducible across runs.
- **Guardrails:** None specific.

### 54. GPU top-k selection

**Definition:** Selecting the k smallest or largest values out of millions of scores on a GPU.

**How it works:**
1. **Radix select:** process score bits from the most significant, count how many values fall in each bucket, and narrow down to the bucket holding the k-th value. Repeat on the next bits.
2. **Warp-level selection:** each GPU thread group keeps a small sorted queue in registers and merges with bitonic sorting networks.
3. Results from many blocks are merged in a final pass.
4. This avoids sorting all N scores.

**Agent use:**
- **Role:** Retriever (GPU-accelerated search).
- **How:** Makes brute-force and IVF search on GPUs fast. The agent batches queries to keep the GPU busy (#106).
- **Rules:** Large k reduces GPU efficiency. Request the k you actually need.
- **Guardrails:** Watch GPU memory per batch. Out-of-memory errors fail whole batches.

### 55. Early abandoning (partial distance computation)

**Definition:** Stopping a distance calculation as soon as it's certain to be worse than the current k-th best.

**How it works:**
1. Keep the current threshold τ, the k-th best distance so far.
2. Compute the squared distance dimension by dimension, keeping a running sum.
3. Since each term is non-negative, once the partial sum exceeds τ, the vector can't qualify. Stop early.
4. Ordering dimensions by variance (largest first, for example after PCA) makes abandoning happen sooner.

**Agent use:**
- **Role:** Retriever (custom brute-force or re-scoring code).
- **How:** Speeds up exact re-scoring of candidate lists, especially in high dimensions after PCA rotation.
- **Rules:** Works for L2 distance. For dot product you need bounds from the remaining norm, using Cauchy-Schwarz.
- **Guardrails:** It conflicts with SIMD-friendly full computation. Benchmark both.

### 56. Triangle-inequality pruning (pivots)

**Definition:** Using precomputed distances to reference points (pivots) to skip vectors that can't be close to the query.

**How it works:**
1. Choose a few pivot vectors and precompute the distance from every vector to each pivot.
2. At query time, compute the distance from the query to each pivot.
3. By the triangle inequality, |d(q, p) − d(x, p)| ≤ d(q, x). That gives a lower bound on the true distance.
4. If the lower bound is already worse than the current k-th best, skip x without computing its full distance.
5. This works for any true metric (L2, angular), but not for raw dot product.

**Agent use:**
- **Role:** Retriever (metric spaces, exact search).
- **How:** Useful for exact search in moderate dimensions, or custom metrics.
- **Rules:** Only valid for true metrics (V3: confirm the metric).
- **Guardrails:** In high dimensions the bounds become loose and pruning stops helping. Measure the skip rate.

## B2. Tree and partition indexes

### 57. KD-tree

**Definition:** A binary tree that recursively splits space along one coordinate at a time.

**How it works:**
1. Pick a dimension (usually the one with the greatest spread) and split the points at its median.
2. Recurse on both halves until the leaves hold few points.
3. **Search:** descend to the leaf containing the query, scan it, and record the best distance.
4. Backtrack: visit the other side of a split only if the splitting plane is closer than the current k-th best.
5. Very efficient in low dimensions (under about 20), but degrades to nearly brute force in high dimensions.

**Agent use:**
- **Role:** Retriever (low-dimensional data).
- **How:** The agent uses KD-trees for geo coordinates, 2D/3D projections, or small engineered features, never for raw embeddings with hundreds of dimensions.
- **Rules:** Choose the index by dimension: trees below about 20 dimensions, graph or IVF above.
- **Guardrails:** If the visited-node count approaches N, the tree has stopped helping. Switch structures.

### 58. Ball tree

**Definition:** A tree where each node is a hypersphere (center and radius) containing its points.

**How it works:**
1. Split the points into two groups, for example around two far-apart points.
2. Each child gets a ball: the centroid of its points and the radius covering them all.
3. Recurse down to small leaves.
4. **Search:** skip any ball whose closest possible point (distance to center minus radius) is worse than the current k-th best.
5. Handles moderate dimensions and non-axis-aligned data better than KD-trees.

**Agent use:**
- **Role:** Retriever (moderate dimensions, custom metrics).
- **How:** A good choice for exact search with unusual metrics on medium-sized data.
- **Rules:** Same dimension rule as #57.
- **Guardrails:** Same degradation check as #57.

### 59. VP-tree (vantage-point tree)

**Definition:** A tree that splits points by their distance to a chosen vantage point: inside versus outside a radius.

**How it works:**
1. Pick a vantage point v.
2. Compute every point's distance to v. The median distance μ splits points into "inside" (≤ μ) and "outside".
3. Recurse on both sets.
4. **Search:** compute d(q, v). Using the triangle inequality, visit "inside" only if d(q, v) − τ ≤ μ, and "outside" only if d(q, v) + τ ≥ μ, where τ is the current k-th best distance.
5. It needs only a distance function, no coordinates.

**Agent use:**
- **Role:** Retriever (any metric space, such as edit distance on strings).
- **How:** The agent uses VP-trees when the similarity isn't a vector at all, for example fuzzy matching of identifiers.
- **Rules:** The distance must be a true metric.
- **Guardrails:** Same high-dimension caution as #57.

### 60. Random projection tree forest (Annoy-style)

**Definition:** Many trees, each splitting space by random hyperplanes, searched together.

**How it works:**
1. Build each tree by picking two random points, splitting by the hyperplane equidistant between them, and recursing until leaves are small.
2. Build many such trees, each with different randomness.
3. **Search:** descend all trees at once with a shared priority queue ordered by distance to the splitting planes, collecting candidates from many leaves.
4. Compute exact distances for the union of candidates and take the top k.
5. More trees and more candidates searched gives better recall but is slower.
6. The index is a static file that can be memory-mapped.

**Agent use:**
- **Role:** Indexer and Retriever (static, read-only corpora).
- **How:** Good for read-only indexes shared across processes via memory mapping. It's simple to build and ship.
- **Rules:** Tune the number of trees and the search budget by measured recall.
- **Guardrails:** The index is static. Updates mean a rebuild, so plan rebuild cadence (#146 in Part 3).

### 61. IVF (inverted file index)

**Definition:** Partitioning vectors into clusters and searching only the clusters nearest the query.

**How it works:**
1. Train k-means (#39) to get C centroids, often around √N to 4√N.
2. Assign each vector to its nearest centroid's list.
3. **Search:** compute the query's distance to all centroids and pick the nprobe nearest (#63).
4. Scan only those lists, computing distances to their vectors.
5. Take the top k.
6. Recall depends on nprobe: neighbors sitting in clusters that weren't probed are missed.

**Agent use:**
- **Role:** Indexer and Retriever.
- **How:** A memory-efficient, easily sharded index. Lists map naturally to disk blocks or shards. The agent tunes C and nprobe with recall measurements.
- **Rules:** Train centroids on representative data; V5 applies to every change of C or nprobe.
- **Guardrails:** Unbalanced lists (#173) make some queries much slower. Monitor list sizes.

### 62. IVF-PQ

**Definition:** IVF partitioning combined with product-quantized codes inside each list.

**How it works:**
1. Train coarse centroids (IVF).
2. For each vector, compute the residual: the vector minus its centroid.
3. Encode the residual with PQ (#35). Residuals are smaller and more uniform, so PQ is more accurate on them.
4. **Search:** pick nprobe lists, build a lookup table per list from the query's residual, and scan the codes with ADC (#43).
5. Optionally re-score the top candidates with full vectors (#93).

**Agent use:**
- **Role:** Indexer (billion-scale in memory).
- **How:** The standard configuration for very large collections on limited RAM. The agent chooses code size, C and nprobe from a recall/latency/memory budget.
- **Rules:** Always measure recall at the operating point; keep full vectors on disk for re-scoring if top-1 accuracy matters.
- **Guardrails:** Retrain both centroids and codebooks when drift appears (#168, #153).

### 63. nprobe and multi-probe tuning

**Definition:** Choosing how many partitions to search per query: the main speed/recall dial in IVF-style indexes.

**How it works:**
1. Rank all centroids by distance to the query.
2. Search the top nprobe lists.
3. Recall rises quickly at first, then flattens. Latency rises roughly linearly with nprobe.
4. **Adaptive variants:** stop probing when the next centroid is much farther than the current k-th result, or set nprobe per query from estimated difficulty.

**Agent use:**
- **Role:** Operator and Retriever.
- **How:** The agent sweeps nprobe on a query sample, plots recall versus latency, and picks the smallest nprobe that meets the recall target (#110).
- **Rules:** Record the chosen nprobe and the recall it achieved with the index version.
- **Guardrails:** Re-tune after large data changes; the same nprobe gives lower recall after drift.

### 64. Inverted multi-index (IMI)

**Definition:** An IVF variant that splits vectors in two halves and clusters each half separately, producing a very large number of fine cells.

**How it works:**
1. Split each vector into two halves.
2. Run k-means with K centroids on each half. The cells are all K × K pairs.
3. Each vector belongs to the cell (its nearest centroid for half 1, its nearest centroid for half 2).
4. **Search:** rank the centroids for each half, then visit cell pairs in order of combined distance, using a priority queue (multi-sequence algorithm).
5. Very fine partitioning with small codebooks.

**Agent use:**
- **Role:** Indexer (very large collections).
- **How:** Gives finer partitions than IVF at the same training cost, which is useful at billion scale.
- **Rules:** Many cells are empty or tiny; check occupancy (#173).
- **Guardrails:** Same tuning discipline as #63.

## B3. Graph indexes

### 65. NSW (navigable small world graph)

**Definition:** A proximity graph where each vector links to nearby vectors, plus some long links, so greedy walking finds near neighbors fast.

**How it works:**
1. Insert vectors one by one. Each new vector links to its nearest neighbors found by searching the current graph.
2. Early insertions create long-range links (the graph was sparse when they were added). Later ones create short links.
3. **Search:** start from an entry point, move to whichever neighbor is closest to the query, and repeat until no neighbor is closer.
4. Long links cross the space quickly; short links refine.
5. It's the predecessor of HNSW.

**Agent use:**
- **Role:** Background for #66–67.
- **How:** Explains why insertion order and connectivity matter in graph indexes.
- **Rules:** Use HNSW or Vamana in practice.
- **Guardrails:** None specific.

### 66. HNSW search

**Definition:** Searching a layered navigable graph: coarse greedy steps in sparse top layers, then a careful search in the dense bottom layer.

**How it works:**
1. Start at the global entry point on the top layer.
2. On each upper layer, greedily move to the neighbor closest to the query until there's no improvement.
3. Use the result as the starting point for the next layer down.
4. On layer 0, run beam search (#68) with a candidate list of size ef ≥ k.
5. Return the best k from the final list.
6. Cost is roughly logarithmic in N for typical data.

**Agent use:**
- **Role:** Retriever (the most common in-memory vector index).
- **How:** The agent sets ef per query: higher for important or "must not miss" searches, lower for fast autocomplete-style lookups.
- **Rules:** ef ≥ k always. Tune ef by measured recall (#110).
- **Guardrails:** Results are approximate (V8). Never conclude absence from them.

### 67. HNSW insertion and neighbor-selection heuristic

**Definition:** How new vectors join the HNSW graph, with pruning that keeps the links diverse.

**How it works:**
1. Draw the new node's top layer at random (exponentially decaying probability).
2. From the entry point, search down to the node's top layer greedily.
3. On each layer from there down, run beam search with efConstruction to find candidate neighbors.
4. **Heuristic selection:** go through candidates nearest first, and add a candidate only if it's closer to the new node than to every neighbor already chosen. This keeps links pointing in different directions.
5. Keep up to M links per node (2M on layer 0). Add reverse links, pruning neighbors that now exceed their limit.

**Agent use:**
- **Role:** Indexer.
- **How:** The agent picks M (memory and recall) and efConstruction (build quality and time). Higher values give better recall but slower builds and more memory.
- **Rules:** Record M and efConstruction with the index (V1-style lineage for the index).
- **Guardrails:** Heavy deletions degrade the graph (#117, #183). Plan repair or rebuild.

### 68. Beam search on graphs (ef / L parameter)

**Definition:** Exploring a proximity graph with a bounded list of best candidates instead of a single greedy path.

**How it works:**
1. Keep two sets: a priority queue of candidates to expand, and a result list of the best ef nodes found.
2. Start with the entry point in both.
3. Repeatedly expand the closest unexpanded candidate: compute the distances of its neighbors, and add improving ones to both sets.
4. Trim the result list to ef.
5. Stop when the closest unexpanded candidate is worse than the worst result in the list.
6. A visited set prevents recomputing distances.

**Agent use:**
- **Role:** Retriever.
- **How:** ef (or L in DiskANN) is the main per-query recall dial for graph indexes.
- **Rules:** Expose ef as a parameter in the agent's search tool, with a safe default and a capped maximum.
- **Guardrails:** Cap the maximum ef (VG3), so one query can't consume excessive CPU.

### 69. Vamana / DiskANN

**Definition:** A single-layer proximity graph designed for SSD-resident billion-scale search.

**How it works:**
1. Start from a random graph and pick the medoid (the most central point) as the entry point.
2. For each point, run a greedy search, then prune its neighbor list with RobustPrune (#70).
3. Do two passes (first α = 1, then α > 1) to get both local and long-range links.
4. **On disk:** store each node's full vector and neighbor list together in one block. Keep PQ-compressed vectors in RAM.
5. **Search:** navigate using the in-RAM PQ distances, read the node blocks from SSD for candidates, and re-rank them with the full vectors from those blocks.

**Agent use:**
- **Role:** Indexer (corpora too large for RAM).
- **How:** Lets the agent serve billion-vector search from a single machine with SSDs. Search cost is dominated by the number of SSD reads.
- **Rules:** Tune L (beam width) and beam I/O width against latency, with recall measurements.
- **Guardrails:** Monitor SSD latency. Shared or slow disks destroy tail latency (#108).

### 70. RobustPrune (α-pruning)

**Definition:** The neighbor-pruning rule in Vamana that keeps diverse links and, with α > 1, long-range ones.

**How it works:**
1. Sort the candidate neighbors of node p by distance to p.
2. Take the nearest remaining candidate c and add it as a neighbor.
3. Remove every remaining candidate x where α × d(c, x) ≤ d(p, x): x is "covered" by c.
4. Repeat until the degree limit R is reached or no candidates remain.
5. α > 1 removes fewer candidates, keeping longer edges, which shortens search paths.

**Agent use:**
- **Role:** Indexer.
- **How:** Explains the α and R parameters the agent tunes in DiskANN-style indexes.
- **Rules:** Common starting values are α around 1.2 and R around 64; tune with recall measurements.
- **Guardrails:** None specific.

### 71. NSG (navigating spreading-out graph)

**Definition:** A single-layer graph built from an approximate kNN graph, with pruning that guarantees the graph is navigable from one entry point.

**How it works:**
1. Build an approximate kNN graph first (for example with NN-descent).
2. Choose the navigating node (near the dataset's center).
3. For each node, search from the navigating node, collect the visited nodes as candidates, and prune them with an MRNG-style rule (similar to #70).
4. Add links to ensure every node is reachable from the navigating node (a spanning tree repair).
5. The result is a sparse graph with short search paths.

**Agent use:**
- **Role:** Indexer.
- **How:** An alternative to HNSW with lower memory use for static data.
- **Rules:** Build offline; it's best for corpora that rarely change.
- **Guardrails:** Updates usually need a rebuild.

### 72. CAGRA (GPU-built graph)

**Definition:** A proximity graph designed for building and searching on GPUs.

**How it works:**
1. Build an initial kNN graph on the GPU (for example with IVF-PQ or NN-descent).
2. Optimize it: reorder edges by rank-based importance, add reverse edges, and prune to a fixed degree.
3. A fixed degree fits the GPU's parallel memory access.
4. **Search:** many parallel threads expand a candidate list together, using hashing for the visited set, with many queries per batch.

**Agent use:**
- **Role:** Indexer (fast builds and high-throughput search on GPUs).
- **How:** Build times drop from hours to minutes, which makes frequent full rebuilds practical. The graph can also be exported to a CPU HNSW for serving.
- **Rules:** Compare recall of the exported or served index against the GPU original.
- **Guardrails:** GPU memory limits the build size; plan sharded builds for larger corpora.

### 73. Entry-point selection

**Definition:** Choosing where graph search begins, which strongly affects speed and recall.

**How it works:**
1. **Fixed:** the medoid of the data (Vamana), or the top-level node (HNSW).
2. **Multiple:** several spread-out seeds, or a random sample.
3. **Learned or partitioned:** pick the entry nearest to the query from a small set of cluster centroids.
4. Good entries shorten the path to the query's region and avoid getting stuck in disconnected or distant parts of the graph.

**Agent use:**
- **Role:** Retriever and Indexer.
- **How:** For multi-modal data (very different topics or tenants in one index), the agent uses centroid-based entry points to improve recall for minority regions.
- **Rules:** Re-evaluate entry points after large data changes.
- **Guardrails:** Measure recall per data segment (topic, tenant), not only overall. Minority segments can fail silently.

### 74. Graph connectivity repair

**Definition:** Detecting and fixing nodes in a proximity graph that are unreachable or poorly connected.

**How it works:**
1. Run a reachability check (BFS) from the entry point(s).
2. Unreached nodes are "islands", usually caused by deletions or aggressive pruning.
3. Count each node's incoming edges. Nodes with zero in-degree can't be found.
4. Repair by re-inserting the affected nodes, or adding edges from their nearest reachable neighbors.
5. Run it periodically or after heavy deletions.

**Agent use:**
- **Role:** Observer and Indexer.
- **How:** The agent tracks the unreachable-node count (#183). If it rises, it schedules a repair or rebuild, because those vectors are effectively deleted from search.
- **Rules:** Run the connectivity check after bulk deletions and before declaring an index healthy.
- **Guardrails:** Unreachable nodes are a silent recall loss. Alert on any nonzero count above a small threshold.

### 75. Filtered-DiskANN (label-aware graphs)

**Definition:** Graph indexes built so that search restricted to a label (tenant, category) still has connected paths.

**How it works:**
1. Each vector has one or more labels.
2. During construction, edges are pruned with label awareness, keeping edges that preserve paths between same-label nodes.
3. Each label gets its own entry point (a label medoid).
4. **Search:** start at the query label's entry point and only traverse nodes with that label (or use them as stepping stones, depending on the variant).
5. Recall stays high even for rare labels.

**Agent use:**
- **Role:** Indexer and Retriever (filtered search at scale).
- **How:** The agent uses this when queries almost always filter by a label with many distinct values, such as tenant or product category.
- **Rules:** Labels must be known at build time. New label values may need a partial rebuild.
- **Guardrails:** VG1: the label filter must be enforced by the search itself, never only by post-processing.

### 76. SPANN (memory-disk hybrid partitions)

**Definition:** An IVF-like design keeping centroids in memory and posting lists on disk, with boundary vectors duplicated into several lists.

**How it works:**
1. Run hierarchical balanced clustering (#42) into many small partitions.
2. Keep the centroids in memory, with a fast graph index over them.
3. Store each partition's vectors on disk.
4. Assign vectors near partition boundaries to multiple partitions, so they're found from either side.
5. **Search:** find the nearest centroids in memory, then read only those partitions from disk. Prune partitions whose centroids are much farther than the best one.

**Agent use:**
- **Role:** Indexer (billion-scale on disk).
- **How:** An alternative to DiskANN with fewer random disk reads per query, since reads are sequential per partition.
- **Rules:** Tune the duplication factor and pruning threshold with recall measurements.
- **Guardrails:** Duplication increases storage. Track total size against the budget.

## B4. Hashing indexes

### 77. Random-hyperplane LSH

**Definition:** Hashing vectors with random hyperplane bits, so similar vectors land in the same bucket with high probability.

**How it works:**
1. Each hash function concatenates b sign bits from random hyperplanes (#31).
2. Build L hash tables, each with its own random hyperplanes.
3. Insert each vector into its bucket in every table.
4. **Search:** hash the query, collect all vectors from its buckets across the L tables, and compute exact distances on that candidate set.
5. Larger b gives fewer candidates (higher precision), and larger L gives more chances to find neighbors (higher recall).

**Agent use:**
- **Role:** Indexer and Retriever (streaming or very simple deployments).
- **How:** Supports cheap inserts and deletes and has theoretical guarantees. It's used for near-duplicate detection and streaming deduplication.
- **Rules:** Tune b and L by recall; LSH typically needs more memory than graph indexes for the same recall.
- **Guardrails:** Monitor the candidate-set size. Overly full buckets turn LSH into brute force.

### 78. Multi-probe LSH

**Definition:** LSH that also checks buckets near the query's bucket, reaching the same recall with fewer tables.

**How it works:**
1. Hash the query as usual.
2. Generate a sequence of perturbed hashes (flip the bits most likely to differ for true neighbors, those where the query was closest to the hyperplane).
3. Probe those buckets in order of likelihood.
4. Stop after a probe budget.

**Agent use:**
- **Role:** Retriever.
- **How:** Cuts LSH memory significantly. The probe count becomes the per-query recall dial.
- **Rules:** Same tuning discipline as #63.
- **Guardrails:** Cap the probes per query (VG3).

### 79. E2LSH (p-stable LSH for L2)

**Definition:** LSH for Euclidean distance, using random projections divided into fixed-width slots.

**How it works:**
1. Hash function h(x) = floor((a · x + b) / w), where a is random Gaussian, b is a random offset and w is the slot width.
2. Nearby points are likely to fall into the same slot.
3. Concatenate several such hashes per table and use many tables, as in #77.
4. The probabilities of collision are known in closed form, allowing parameter choices with guarantees.

**Agent use:**
- **Role:** Retriever (unnormalized L2 spaces).
- **How:** Used when the distance is Euclidean and vectors aren't normalized.
- **Rules:** Tune w to the typical neighbor distance in the data.
- **Guardrails:** Same as #77.

## B5. Filtering, hybrid search and fusion

### 80. Pre-filtering

**Definition:** Applying metadata filters first, then searching only the vectors that pass.

**How it works:**
1. Evaluate the filter (tenant = X, date > Y) on the metadata index, producing an allow-list or bitmap.
2. Run the vector search restricted to that set: brute force over the set, or an index search that skips non-allowed nodes.
3. Results are always correct with respect to the filter.
4. With very selective filters, brute force over the small set is fast and exact.
5. With moderately selective filters inside graph indexes, skipping many nodes can break navigation and hurt recall (#82 fixes this).

**Agent use:**
- **Role:** Retriever (security and correctness).
- **How:** The agent always applies access filters this way (VG1), so unauthorized content can't appear in results or influence ranking.
- **Rules:** Security filters are never post-filters.
- **Guardrails:** Test filtered recall separately (#156) at different selectivities.

### 81. Post-filtering with oversampling

**Definition:** Searching without filters, then removing results that fail the filter, retrieving extra results to compensate.

**How it works:**
1. Search for k × f results (f is the oversampling factor, for example 4–10).
2. Remove the results that fail the filter.
3. Return the top k remaining.
4. If fewer than k remain, retry with a larger f, or switch to pre-filtering.
5. Fast when most vectors pass the filter. Fails badly when few do.

**Agent use:**
- **Role:** Retriever (non-security filters only).
- **How:** Acceptable for soft filters (language preference, freshness) where the filter passes most vectors.
- **Rules:** Use only for non-security filters. Report when fewer than k results survived.
- **Guardrails:** Never use post-filtering for tenant or ACL filters (VG1). Unauthorized vectors would still be scored and could leak via timing or counts.

### 82. In-graph filtering (ACORN-style)

**Definition:** Graph search that traverses only allowed nodes, with a denser graph so the allowed subgraph stays navigable.

**How it works:**
1. Build the graph with more edges than usual (more neighbors per node, or neighbor expansion at search time).
2. **Search:** when expanding a node, skip neighbors that fail the filter. Also look at the neighbors of neighbors, so connectivity holds even when many direct neighbors are filtered out.
3. The search stays within the allowed set while keeping good recall.
4. It works for arbitrary filter predicates, not only pre-declared labels.

**Agent use:**
- **Role:** Retriever (frequent arbitrary filters).
- **How:** The agent uses it when filters vary widely and are combined at query time.
- **Rules:** Measure recall at low selectivity (where 1–5% of vectors pass); that's where naive filtering fails.
- **Guardrails:** The extra edges cost memory. Budget for it.

### 83. Selectivity-based query planning

**Definition:** Choosing the search strategy for each query from how many vectors pass its filter.

**How it works:**
1. Estimate the filter's selectivity from metadata statistics or bitmap counts.
2. **Very selective** (few thousand matches): brute force over the allowed set. Exact and fast.
3. **Moderately selective:** filtered index search (#82) or pre-filtered IVF.
4. **Barely selective** (most pass): normal index search with a filter check, or post-filtering for soft filters.
5. Thresholds are tuned by benchmarks.

**Agent use:**
- **Role:** Retriever.
- **How:** Prevents the two classic failures: slow searches on broad filters and missing results on narrow filters.
- **Rules:** Log the chosen strategy per query, so recall and latency problems can be traced (#191).
- **Guardrails:** Security filters (VG1) are always enforced inside whichever strategy is chosen.

### 84. Partitioned (per-tenant or per-collection) indexes

**Definition:** Keeping a separate index for each tenant, collection or other hard boundary.

**How it works:**
1. Route each vector to the index for its partition key.
2. Each index is built and tuned independently.
3. A query is routed only to the partition(s) it's allowed to search.
4. Small partitions can use brute force; large ones get ANN indexes.
5. Deleting a tenant means dropping its whole index.

**Agent use:**
- **Role:** Indexer and Retriever (isolation).
- **How:** The strongest isolation: a query physically can't touch other tenants' data, and tenant deletion is clean and verifiable (V6).
- **Rules:** Use partitions for hard boundaries (tenants, legal data domains), and filters for soft ones.
- **Guardrails:** Many tiny partitions waste overhead. Group very small tenants into a shared index with strict pre-filters.

### 85. BM25 keyword retrieval

**Definition:** Classic keyword relevance scoring, used as the sparse half of hybrid search.

**How it works:**
1. Index the terms in an inverted index.
2. For each query term, compute IDF (rare terms weigh more).
3. Score each document by summing, over query terms, IDF × a saturated term frequency normalized for document length (parameters k1 and b).
4. Retrieve the top k with WAND or Block-Max WAND.

**Agent use:**
- **Role:** Retriever.
- **How:** Catches exact identifiers, error codes, names and rare words that dense vectors miss. The agent always includes it in hybrid search for technical content.
- **Rules:** Same analyzer at index and query time (V3).
- **Guardrails:** BM25 can't handle synonyms; don't use it alone for natural-language questions.

### 86. Sparse-dense hybrid retrieval

**Definition:** Running keyword (sparse) and semantic (dense) retrieval together and combining the results.

**How it works:**
1. Run sparse retrieval (BM25 or SPLADE) and dense retrieval in parallel.
2. Each returns a ranked list with scores.
3. Combine them with rank fusion (#87) or score fusion (#88).
4. Optionally rerank the merged top results (#94).
5. Some engines compute a joint score in one index pass, using a weighted sum of sparse and dense dot products.

**Agent use:**
- **Role:** Retriever (the recommended default).
- **How:** Gives robust results across query types: exact identifiers and natural-language questions.
- **Rules:** Evaluate the fusion weights on a golden query set (#164).
- **Guardrails:** Apply the same access filters to both channels (VG1).

### 87. Reciprocal Rank Fusion (RRF)

**Definition:** Combining ranked lists using only ranks: score = Σ 1 / (k + rank).

**How it works:**
1. For each document, look up its rank in each list.
2. Add 1 / (k + rank) for each list it appears in. k is a constant, commonly 60.
3. Documents absent from a list get nothing from it.
4. Sort by the summed score.
5. Robust because it ignores score scales, which differ wildly between systems.

**Agent use:**
- **Role:** Retriever.
- **How:** The agent's default way to merge hybrid channels, or results from several query rewrites (#92). No calibration needed.
- **Rules:** Retrieve enough from each channel (for example 50–100) before fusion, so good documents aren't cut early.
- **Guardrails:** None specific.

### 88. Score-normalized fusion (convex combination)

**Definition:** Normalizing each channel's scores to a common scale, then combining them with weights.

**How it works:**
1. Normalize each channel's scores: min-max to [0, 1], z-score, or calibrated probabilities (#20).
2. Fused score = w × dense + (1 − w) × sparse.
3. Tune w on labeled queries.
4. Can outperform RRF when well tuned, because it uses score magnitudes, not just order.

**Agent use:**
- **Role:** Retriever (when labeled data exists).
- **How:** The agent tunes w per corpus or per query type (identifier-heavy versus natural language).
- **Rules:** Re-tune after any model or analyzer change.
- **Guardrails:** Min-max normalization is sensitive to outliers in the top score. Prefer calibrated or z-score normalization.

### 89. Maximal Marginal Relevance (MMR)

**Definition:** Re-ranking to balance relevance and diversity, so the results aren't near-duplicates of each other.

**How it works:**
1. Start with an empty selection.
2. For each remaining candidate, compute λ × relevance to the query − (1 − λ) × its highest similarity to anything already selected.
3. Add the candidate with the highest value.
4. Repeat until k items are selected.
5. λ near 1 favors relevance; λ near 0 favors diversity.

**Agent use:**
- **Role:** Retriever (context building).
- **How:** Prevents the agent's context from filling with five overlapping chunks of the same paragraph (common with overlapping chunks, #11), leaving room for other relevant sources.
- **Rules:** Apply it after relevance retrieval, on a larger candidate pool.
- **Guardrails:** Too much diversity drops the most relevant duplicates; keep λ fairly high (0.5–0.8) for factual retrieval.

### 90. Range (radius) search

**Definition:** Returning all vectors within a distance threshold, instead of a fixed k.

**How it works:**
1. Set a radius r (or a similarity threshold).
2. Search the index for all candidates with distance ≤ r. Graph and IVF indexes expand until the candidates exceed r.
3. Return every match, possibly capped at a maximum count.
4. The result size varies by query: zero to many.

**Agent use:**
- **Role:** Retriever and Indexer (deduplication, "anything similar enough").
- **How:** Used for duplicate detection before insert (#145), or for "show everything about this topic above relevance X" with calibrated scores (#20).
- **Rules:** Use calibrated thresholds; raw cosine thresholds don't transfer across models.
- **Guardrails:** Always cap the result count (V7). A too-loose radius returns the whole corpus.

### 91. Multi-vector (MaxSim) retrieval pipelines

**Definition:** Searching with token-level vectors (late interaction), usually in candidate-generation plus exact-scoring stages.

**How it works:**
1. **Candidate generation:** each query token searches an ANN index of document token vectors (or their centroids, #48). The documents owning the hits become candidates.
2. **Scoring:** for each candidate, compute the full MaxSim score (#47).
3. Rank by MaxSim and return the top k.
4. Pruning (centroid-based scores) cuts candidates before exact scoring.

**Agent use:**
- **Role:** Retriever (high precision on detail-heavy queries).
- **How:** The agent uses it for legal, technical or code queries where exact details matter, often as a second stage after a cheap first stage.
- **Rules:** Measure the gain against single-vector plus cross-encoder reranking; it isn't always better.
- **Guardrails:** Budget the latency. Token-level search multiplies the work per query.

### 92. Multi-query expansion

**Definition:** Rewriting one query into several variants, searching each, and fusing the results.

**How it works:**
1. Generate variants: paraphrases, sub-questions, keyword versions, versions with expanded acronyms.
2. Run each variant through retrieval.
3. Fuse the lists with RRF (#87).
4. Deduplicate and optionally rerank.

**Agent use:**
- **Role:** Retriever.
- **How:** Raises recall for vague or compound questions ("how does auth work and where are tokens refreshed?"). The agent splits it into sub-queries.
- **Rules:** Keep the original query as one of the variants.
- **Guardrails:** Limit the variant count (cost and latency, VG3). Variants generated by a model can drift off topic, so check the fused results against the original question.

## B6. Re-scoring and reranking

### 93. Re-scoring with full-precision vectors

**Definition:** Retrieving extra candidates with a compressed index, then re-ranking them with full-precision vectors.

**How it works:**
1. Search the compressed index (PQ, int8 or binary) for k × f candidates.
2. Fetch the full-precision vectors for those candidates, from RAM or disk.
3. Compute exact distances.
4. Sort and return the top k.
5. Recovers most of the recall lost to compression, at the cost of fetching f × k vectors.

**Agent use:**
- **Role:** Retriever.
- **How:** The agent's default pattern whenever quantization is used (#33–38). It tunes f by measured recall.
- **Rules:** Store full vectors alongside the compressed index when quantizing.
- **Guardrails:** Re-scoring reads from disk can dominate latency. Monitor it (#178).

### 94. Cross-encoder reranking

**Definition:** Re-scoring the top candidates with a model that reads the query and the candidate text together.

**How it works:**
1. Take the top 20–200 candidates from first-stage retrieval.
2. For each, feed "query + candidate text" into a cross-encoder transformer.
3. The model outputs a relevance score, using full attention between query and candidate.
4. Sort by that score and keep the top k.
5. Much more accurate than vector similarity, but too slow to run over the whole corpus.

**Agent use:**
- **Role:** Retriever (precision before generation).
- **How:** The agent reranks before putting chunks into its context, so the few slots go to the truly relevant passages. Fewer irrelevant chunks means fewer wrong answers.
- **Rules:** Rerank only what first-stage retrieval found; log both rankings.
- **Guardrails:** Cap the candidate count and use timeouts. On timeout, fall back to first-stage ranking rather than failing.

### 95. Multi-stage retrieval funnel

**Definition:** A pipeline of progressively more expensive, more accurate scoring stages over shrinking candidate sets.

**How it works:**
1. **Stage 1:** a very cheap search (binary or PQ codes) over the whole corpus, giving thousands of candidates.
2. **Stage 2:** int8 or full-vector re-scoring, giving hundreds.
3. **Stage 3:** a cross-encoder or late-interaction model, giving tens.
4. **Stage 4 (optional):** an LLM listwise reranker (#96), giving the final few.
5. Each stage's cutoff is tuned so that relevant items survive.

**Agent use:**
- **Role:** Retriever (architecture).
- **How:** The agent designs retrieval as a funnel with explicit per-stage budgets for latency and cost.
- **Rules:** Measure per-stage recall: did the relevant item survive each stage? (#191)
- **Guardrails:** A stage that drops relevant items silently caps quality for every later stage. Monitor survival rates.

### 96. LLM listwise reranking

**Definition:** Asking a language model to order a small list of candidates by relevance to the query.

**How it works:**
1. Give the model the query and a numbered list of candidate passages (for example 10–20).
2. Ask for a ranked list of IDs, or relevance labels.
3. For longer lists, rerank in sliding windows from the bottom up, so good items bubble to the top.
4. Parse and validate the output: every ID present once, no invented IDs.

**Agent use:**
- **Role:** Retriever (final-stage judgment).
- **How:** Useful when relevance needs reasoning ("does this passage actually answer the question?").
- **Rules:** Validate the model's output strictly. On parse failure, fall back to the previous stage's order.
- **Guardrails:** Candidate passages are untrusted data (VG6). Instructions inside them ("rank me first") must be ignored. Keep a clear separation between the instruction and the passages.

### 97. HyDE (hypothetical document embeddings)

**Definition:** Generating a hypothetical answer to the query, embedding that, and searching with it.

**How it works:**
1. Ask a language model to write a plausible answer passage for the query.
2. Embed the generated passage instead of (or alongside) the raw query.
3. Search with that embedding. The generated passage looks like real documents, so it often lands closer to them than a short question does.
4. Fuse with the original-query results.

**Agent use:**
- **Role:** Retriever (short or vague queries).
- **How:** Improves recall when queries are short and documents are long.
- **Rules:** Use the hypothetical passage only for retrieval, never as an answer or a source.
- **Guardrails:** The generated text can be wrong and steer retrieval toward wrong topics. Always fuse with the original query, and check the results.

### 98. Query routing

**Definition:** Deciding which index, collection or retrieval strategy a query should go to.

**How it works:**
1. Classify the query: by keywords, a small classifier, an LLM decision, or similarity to collection descriptions or centroids.
2. Route to the relevant collection(s): code index, docs index, tickets index.
3. Choose the strategy per route (hybrid weights, filters, reranker).
4. Fall back to searching several collections when the classifier isn't confident.

**Agent use:**
- **Role:** Retriever (multi-source agents).
- **How:** The agent avoids searching everything for every question, which saves cost and reduces noise.
- **Rules:** Log the routing decision and confidence per query (#191).
- **Guardrails:** On low confidence, search several routes instead of guessing one. Routing must never bypass access filters (VG1).

## B7. Distributed search and performance

### 99. Sharded scatter-gather search

**Definition:** Splitting the vector collection across shards, querying all of them in parallel, and merging results.

**How it works:**
1. Distribute vectors across shards, randomly or by hash.
2. A coordinator sends the query to every shard.
3. Each shard returns its local top k′ (slightly more than k, for safety).
4. The coordinator merges with a heap (#103) and returns the global top k.
5. Latency is set by the slowest shard.

**Agent use:**
- **Role:** Retriever (scale beyond one machine).
- **How:** The standard way to scale. The agent watches for missing shards in results.
- **Rules:** Results report how many shards answered.
- **Guardrails:** A partial answer (some shards timed out) must be flagged as partial, never presented as complete.

### 100. Partition-aware shard routing

**Definition:** Placing vectors on shards by cluster, so each query only needs a few shards.

**How it works:**
1. Cluster the vectors (#39, #42) and assign whole clusters to shards.
2. Keep the centroid-to-shard map at the coordinator.
3. For a query, find the nearest centroids and query only the shards holding them.
4. Fewer shards per query means less total work and higher throughput.
5. Popular clusters can be replicated more (#101).

**Agent use:**
- **Role:** Retriever and Operator.
- **How:** Raises throughput for very large deployments, at the cost of uneven load and possible recall loss at cluster edges.
- **Rules:** Measure recall against full scatter-gather on a query sample.
- **Guardrails:** Hot clusters create hot shards. Monitor per-shard load and rebalance (#139 in Part 3).

### 101. Replication and load balancing

**Definition:** Keeping several copies of each shard and spreading queries across them.

**How it works:**
1. Each shard has R replicas on different machines.
2. A load balancer sends each query to one replica per shard: round-robin, least-loaded, or lowest-latency.
3. Replicas give higher throughput and survive machine failures.
4. Writes must reach all replicas (#135 in Part 3).

**Agent use:**
- **Role:** Operator.
- **How:** The agent sizes replicas from peak query load and the required availability.
- **Rules:** Health-check replicas and remove unhealthy ones from rotation.
- **Guardrails:** Replicas can lag behind on updates. Freshness-sensitive queries need consistency controls (#134).

### 102. Hedged requests

**Definition:** Sending a backup request to another replica when the first is slow, and using whichever answers first.

**How it works:**
1. Send the shard request to replica A.
2. If there's no answer after a delay (for example the 95th-percentile latency), send the same request to replica B.
3. Use the first response and cancel the other.
4. This costs a few percent extra load and greatly cuts tail latency.

**Agent use:**
- **Role:** Retriever.
- **How:** Keeps the agent's many retrieval calls from stalling on one slow node.
- **Rules:** Hedge only read-only requests.
- **Guardrails:** Never hedge writes.

### 103. k-way merge of shard results

**Definition:** Combining sorted top-k lists from many shards into one global top k.

**How it works:**
1. Each shard's list is sorted by score.
2. Push the head of each list into a heap.
3. Pop the best, output it, and push the next item from the same shard.
4. Stop after k outputs.
5. Deduplicate by ID if vectors can live on several shards (as with SPANN duplication, #76).

**Agent use:**
- **Role:** Retriever.
- **How:** Used whenever the agent fans a query out to several shards, collections or query variants.
- **Rules:** Scores must be comparable across shards (same model and metric, V2).
- **Guardrails:** Merging scores from different models is invalid. Use rank fusion (#87) for mixed sources.

### 104. Query-embedding and result caching

**Definition:** Caching the embedding of repeated queries, and the results of repeated searches.

**How it works:**
1. **Embedding cache:** key = normalized query text + model and config. Value = query vector.
2. **Result cache:** key = query vector or text + filters + index version. Value = result list.
3. A changed index version invalidates the results automatically (via the key).
4. LRU or TTL eviction.

**Agent use:**
- **Role:** Retriever.
- **How:** Agents repeat queries often. Caching saves both embedding calls and search work.
- **Rules:** Filters, including tenant and ACL, must be part of the result-cache key (VG1).
- **Guardrails:** Never share cached results across users with different permissions.

### 105. Semantic cache

**Definition:** Reusing a previous answer when a new query is semantically close to a cached one.

**How it works:**
1. Embed the incoming query.
2. Search a cache index of previous queries.
3. If the nearest cached query is above a similarity threshold, return its stored result or answer.
4. Otherwise run the full pipeline and add the result to the cache.

**Agent use:**
- **Role:** Retriever (cost reduction for repeated questions).
- **How:** Useful for FAQ-style traffic with many paraphrases of the same questions.
- **Rules:** Use a high, calibrated threshold, and scope the cache by tenant and permissions.
- **Guardrails:** Similar wording can mean different things ("cancel my order" versus "can I cancel an order?"). Evaluate the false-hit rate on a labeled sample, and expire entries when the underlying data changes.

### 106. Query batching

**Definition:** Grouping concurrent queries into batches, so they're processed together for better hardware utilization.

**How it works:**
1. Collect incoming queries for a short window (a few milliseconds) or until the batch is full.
2. Embed them together (#14) and search them together (matrix operations, #51).
3. Return each result to its caller.
4. Throughput rises a lot; each query waits at most the batching window.

**Agent use:**
- **Role:** Retriever (high-throughput services, GPU search).
- **How:** The agent's multi-query expansions (#92) and sub-agent queries can be batched into one call.
- **Rules:** Keep the batching window small relative to the latency target.
- **Guardrails:** Isolate tenants within a batch: results and filters stay per query (VG1).

### 107. Memory tiering (RAM, mmap, SSD)

**Definition:** Placing hot index data in RAM and colder data on SSD, often through memory-mapped files.

**How it works:**
1. Keep small, frequently accessed structures in RAM: centroids, graph upper layers, compressed codes.
2. Keep large structures on SSD: full vectors, posting lists, graph neighbor blocks.
3. Memory mapping lets the OS cache hot pages automatically.
4. Pinning or warm-up loads critical pages before serving traffic.

**Agent use:**
- **Role:** Operator.
- **How:** Lets the agent plan large indexes on cheaper hardware with predictable latency.
- **Rules:** Warm the cache before sending production traffic to a new index (#123 in Part 3).
- **Guardrails:** When the hot set exceeds RAM, the OS evicts pages and latency spikes. Monitor page-fault rates and cache hit ratio (#185).

### 108. Disk I/O scheduling for disk-based ANN

**Definition:** Organizing SSD reads during graph or partition search to minimize latency.

**How it works:**
1. Store each node's neighbors and vector together in one aligned 4 KB block, so one read gets both.
2. **Beam I/O:** read several candidate nodes' blocks in parallel per search step, rather than one at a time.
3. Use asynchronous I/O (io_uring or similar) for high queue depth.
4. Cache frequently visited nodes (near the entry point) in RAM.

**Agent use:**
- **Role:** Operator.
- **How:** The agent tunes beam width and cache size from measured SSD latency and recall.
- **Rules:** Benchmark on the production storage type. Cloud volumes behave very differently from local NVMe.
- **Guardrails:** Noisy neighbors on shared storage ruin tail latency. Alert on SSD latency percentiles.

### 109. Admission control and rate limiting

**Definition:** Limiting incoming query and ingestion load so the system stays healthy under overload.

**How it works:**
1. **Token bucket:** each client gets tokens at a fixed rate, and each request uses one. Requests without tokens are rejected or delayed.
2. **Concurrency limits** per tenant and globally.
3. **Load shedding:** under overload, reject low-priority requests first, or reduce quality (lower ef, skip reranking).
4. Return clear "retry later" responses.

**Agent use:**
- **Role:** Operator and Retriever.
- **How:** Protects the system from runaway agent loops, a common real-world cause of overload. The agent itself respects rate-limit responses with backoff.
- **Rules:** Each agent and sub-agent has its own query budget.
- **Guardrails:** Degraded mode (lower recall) must be visible in the response metadata, never silent.

### 110. Search-parameter autotuning

**Definition:** Automatically choosing index parameters (ef, nprobe, re-score factor) to meet a recall target at the lowest latency.

**How it works:**
1. Take a representative query sample and compute exact ground truth (#51, #157).
2. Sweep the parameter grid: for each setting, measure recall@k and latency percentiles.
3. Build the recall-versus-latency Pareto curve.
4. Pick the cheapest setting meeting the recall target (for example recall@10 ≥ 0.95).
5. Re-run periodically and after data or model changes.

**Agent use:**
- **Role:** Operator and Observer.
- **How:** The agent tunes on evidence rather than defaults, and records the chosen settings with their measured recall (V5).
- **Rules:** Tune on queries that match real traffic, including filtered queries.
- **Guardrails:** Re-tune after drift (#168). Old settings silently lose recall as data changes.
